## 2. Open-Question Resolutions (master plan §10)

### Q2 — `<name>.test.md` placement

> Should `<name>.test.md` files live ALONGSIDE SKILL.md (in same dir) or in a separate `.claude/skills-tests/` tree?

**Decision: ALONGSIDE.** Path: `.claude/skills/<name>/<name>.test.md` (sibling to SKILL.md).

Rationale (cite-by-cite):
1. claudekit-skills.md:34 ("Progressive disclosure 3-tier" + "references/" subdir convention) — claudekit colocates per-skill assets in the skill dir; tests are a per-skill asset. Splitting them into a parallel tree breaks the "everything for skill X is in `.claude/skills/x/`" mental model.
2. Master plan Appendix B ("File Path Conventions for Phase 5") line 538 already specifies `.claude/skills/<name>/<name>.test.md` (sibling to SKILL.md) and line 539 specifies `.claude/skills/<name>/references/<topic>.md`. The plan is explicit; this resolution confirms it.
3. The validator has zero work to support sibling files — it already iterates `.claude/skills/<name>/` and reads SKILL.md; reading a second deterministic filename is one extra `existsSync` call. A separate tree would require a second top-level scan AND a name-correlation step.
4. claudekit-style validators ("ck-style") explicitly tolerate multiple `.md` per skill dir (claudekit-skills.md:35–46 lists `references/`, `scripts/`, etc. as cohabiting siblings). No choking risk.

**Open implementer escape hatch**: if `claude-code` ever adds an auto-loader that treats every `.md` in `.claude/skills/X/` as part of SKILL.md context, the implementer of 5.2.8 should rename `<name>.test.md` → `<name>.test.spec.md` to keep extension distinct. Default still `<name>.test.md`.

### Q3 — 200-char description limit: hard error vs warning

> Currently 3 Orch skills exceed it (subagent-driven-development 258, claude-code-hooks 247, confusion-protocol 222).

**Decision: warning in v2.0; hard-error in v2.1.**

Rationale:
1. Master plan §10 default explicitly recommends this two-step path. Confirmed.
2. Three of the 13 skills (23%) currently violate. Hard-erroring would block 5.2.2 from exiting 0 against the existing tree, blocking SC-4. The validator MUST be passable on day-1 over the unmodified tree to avoid a chicken-and-egg.
3. 5.2.5 + 5.2.6 (refactor sets) DO refactor those bodies; they MAY also tighten the description as a side effect. After 5.2.6 lands, a follow-on may flip `severity: warn` → `severity: error` for the description-length rule. That flip is a 1-line config change, deferred to Phase 5.5 close-out (or v2.1).
4. The validator emits warnings to stderr with a counted summary at the end (e.g. `WARN: 3 skills exceed description-length limit (200 chars)`). Treating warnings as forensic-but-non-blocking matches `eslint --max-warnings=N` convention.

**Implementer note (5.2.2)**: validator output schema is `{errors: Issue[], warnings: Issue[]}`; CLI prints both, exits 0 if `errors.length === 0` and prints `WARNINGS: N` summary. CI grep can later flip the gate.

// scripts/skills-validate.schema.ts
import { z } from 'zod';

// Frontmatter schema (SKILL.md YAML between `---` fences)
export const SkillFrontmatterSchema = z.object({
  name: z.string().regex(/^[a-z0-9][a-z0-9-]*[a-z0-9]$/, 'must be kebab-case'),
  description: z.string().min(1),
  // 'allowed-tools': comma-separated string OR array of strings.
  // Optional in v2.0 (Q3 deferred); enforced as required AFTER 5.2.7 lands by flipping
  // the schema to .nonoptional() — but at 5.2.2-impl time it stays optional + warning.
  'allowed-tools': z.union([z.string(), z.array(z.string())]).optional(),
  // Optional metadata fields tolerated:
  model: z.string().optional(),
  tools: z.array(z.string()).optional(),
}).passthrough(); // unknown frontmatter keys = warning, not error

export type SkillFrontmatter = z.infer<typeof SkillFrontmatterSchema>;

// Issue model emitted by the validator
export type IssueSeverity = 'error' | 'warning';
export interface Issue {
  severity: IssueSeverity;
  rule: string;             // 'frontmatter-required' | 'name-mismatch' | 'oversize-body' | 'missing-allowed-tools' | 'description-too-long' | 'missing-sibling-test' | 'test-missing-assertions' | ...
  skill: string;            // skill dir name
  file: string;             // absolute path
  line?: number;            // when applicable
  message: string;
}

export interface ValidationResult {
  errors: Issue[];
  warnings: Issue[];
  scannedSkills: number;
}
```

CLI shape:
```

#### C. Behavior contract

1. Discovers skills by globbing `.claude/skills/*/SKILL.md`. The `*` segment is the canonical skill name.
2. For each SKILL.md: parses YAML frontmatter (between leading `---` and next `---`); fails with `frontmatter-required` ERROR if absent or unparseable.
3. Asserts `frontmatter.name === <dirname>` (rule: `name-mismatch`, severity: error). Defends G-3 / G-6 (drift between names).
4. Counts body lines (lines after the second `---`); if > `maxBodyLines` → `oversize-body` ERROR (after 5.2.5/6 land; warn-only until then via `--legacy` flag — see §3.5).
5. Description char count > `maxDescriptionChars` → `description-too-long` WARNING in v2.0 (Q3); becomes ERROR via `--strict` in v2.1.
6. `allowed-tools` missing → WARNING pre-5.2.7, ERROR post-5.2.7 when `requireAllowedTools=true`.
7. Sibling `<name>.test.md` missing → WARNING pre-5.2.8, ERROR post-5.2.8.
8. Sibling test must contain headings `## Trigger`, `## Expected behavior (PASS)`, `## Named failure modes`, `## Assertions` (regex-match `^## Assertions`); the Assertions section must list ≥`minAssertionsPerTest` ordered items. Missing → ERROR per rule (`test-missing-section`, `test-missing-assertions`).
9. The validator NEVER mutates files. `--fix-suggest` emits to stdout only.
10. Exit code: `0` if `errors.length === 0`; `1` otherwise. Warnings are reported to stderr but do not change exit.

```typescript
// packages/core/src/telemetry/component-telemetry.schema.ts
import { z } from 'zod';

export const ComponentEventSchema = z.object({
  ts: z.string().datetime(),
  component_type: z.enum(['skill', 'agent', 'command', 'hook']),
  component_name: z.string().min(1),
  trigger: z.enum([
    'keyword_match',
    'explicit_invoke',
    'agent_dispatch',
    'hook_event',
    'user_prompt',
    'sched_idle',
  ]),
  outcome: z.enum(['ok', 'reject', 'timeout', 'error', 'no_op']),
  tokens_self: z.number().int().min(0).optional(),
  tokens_real: z.number().int().min(0).optional(),
  duration_ms: z.number().int().min(0),
  session_id: z.string().nullable(),
  task_id: z.string().nullable(),
  decision: z.enum(['approve', 'deny', 'modify']).optional(),
  failure_mode: z.enum(['A', 'B', 'C', 'D', 'E', 'F', 'G']).nullable(),
}).strict();  // unknown fields rejected (defends schema drift)

export type ComponentEvent = z.infer<typeof ComponentEventSchema>;

// Helper for ad-hoc readers (rollup script, future Phase 6 dashboards):
export function parseTelemetryLine(line: string): ComponentEvent | null {
  try {
    return ComponentEventSchema.parse(JSON.parse(line));
  } catch {
    return null;  // malformed lines are skipped, not thrown — append-only durability
  }
}
```

# Function-equivalent sections (bash; defensive set -uo pipefail; trap 'exit 0' ERR per project convention):
#   classify_component()       → reads HOOK_EVENT_NAME, tool name, agent_id; emits component_type + component_name + trigger

#### C. Behavior contract

1. Hook script invoked from `.claude/settings.json` for `PostToolUse`, `SubagentStop`, `SessionStart`. **Each event = at most one JSONL line.** Hook reads stdin JSON, computes the event, appends, exits 0. Total budget: <50 ms p99 (target).
2. Script is daemon-dumb: zero LLM calls, zero network calls. Pure shell + `node -e "…"` for JSON in/out (matches existing `budget-watchdog.sh` pattern at lines 28–46).
3. Component classification:
   - PostToolUse where tool name matches `^skill:(\w+)$` → `component_type=skill, trigger=keyword_match` (claude-code-skills emit this when a skill activates per matcher).
   - PostToolUse where tool name is `Task` (= subagent dispatch) → `component_type=agent, component_name=<agent name from payload>, trigger=agent_dispatch`.
   - PostToolUse where tool name starts with `slash:` or matches a `.claude/commands/` filename → `component_type=command, trigger=explicit_invoke`.
   - SubagentStop → `component_type=agent, trigger=agent_dispatch, outcome` derived from payload `status`.
   - SessionStart, Stop, PreToolUse hook fires themselves → `component_type=hook, component_name=<hook name>, trigger=hook_event`.
4. `tokens_real` = current `.transcript-tokens` minus value at start of this hook chain (script reads/writes `.transcript-tokens-prev` snapshot).
5. `duration_ms` = elapsed since previous hook event for the same `session_id` (stored in `.last-event-ts-<session_id>`).
6. `outcome` defaults to `ok` unless payload contains `error` field or status indicates failure (`error`, `timeout`, `denied` → mapped to enum).
7. `failure_mode` populated only when the watchdog logs at the same wallclock minute show a Mode A/B/C event — left `null` otherwise (5.2.3 implementer adds `correlate_failure_mode()` helper that reads `.autonomous-stop-watchdog.log` last 5 lines).
8. Rotation at 10 MB; keep last 5 segments (`*.jsonl.1` … `*.jsonl.5`); older segments deleted via `rm -f`. Defends G-rationale: telemetry over-fires not allowed to consume disk.
