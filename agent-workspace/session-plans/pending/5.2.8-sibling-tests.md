## §F. Subagent Dispatch Protocol (formal)

**Decision: 13× `task-implementer` (sonnet, fresh-context-per-skill) + 1× `task-implementer` (sonnet, finalizer)**, NOT a single `sandwich-dev`. Rationale:
- Architect §8.1 row for 5.2.8 explicitly specifies "task-implementer ×13, fresh-context per skill, 4 parallel batches".
- Each per-skill dispatch is small (~12K tokens — read 1 SKILL.md + write 1 small `.test.md`) → fits FOCUSED_IMPL envelope cleanly.
- Fresh context per skill is the design requirement: it forces each implementer to re-read its target SKILL.md, preventing assumption-pollution that would happen in a single sandwich-dev plowing through all 13.
- The finalizer is also `task-implementer` (not sandwich-dev) because it's a 2-edit surgical task — fits FOCUSED_IMPL.

**Dispatch rules (orchestrator-side):**
1. Every Agent dispatch uses `run_in_background: true` (project hard rule per CLAUDE.md & MEMORY.md).
2. Within a batch, all dispatches are issued in the SAME response (true parallelism).
3. Wait for ALL batch returns before composing the next batch's prompts (orchestrator does not interleave batches).
4. Orchestrator does NOT write code itself during 5.2.8 — only `Agent` and `Read` tool_uses are permitted in the orchestrator transcript (subagent-driven-development invariant).
5. If any per-skill dispatch returns `BLOCKED` / `ESCALATED`: STOP. Write `agent-workspace/memory/escalation.md` with the failing skill's name + the implementer's blocker message. Do NOT proceed to the finalizer.
6. The finalizer dispatch ONLY fires after Subtask 5 (whole-tree validator dry-run) passes — orchestrator confirms pre-flip cleanliness FIRST.
7. Each implementer's completion YAML is parsed; the orchestrator's transcript explicitly cites the parsed values in the next-batch composition (audit trail).

## §H. Open Questions / Risks (architect's autonomous-mode resolutions)

1. **Q: Some skills have very thin SKILL.md content (`grammy-bot`, `nestjs-module`, `claude-code-hooks` post-5.2.6 are all ≤66 lines, mostly Anti-Patterns lists). Can the implementer derive ≥3 *meaningful* failure modes from each?**

For Batch C/D skills (post-refactor), the `references/*.md` files are also readable by the implementer and contain the full failure-mode catalog. This plan's per-skill task table pre-extracts ≥3 modes from each — the implementer can use the table verbatim or expand. Default: use table verbatim.

2. **Q: Architect §3.7.B template has 5 H2 sections, but validator (`scripts/skills-validate.ts:147`) `REQUIRED_TEST_HEADINGS` lists only 4 (`## Trigger`, `## Expected behavior (PASS)`, `## Named failure modes`, `## Assertions`). Should `## Metrics targets` be omitted, or kept as architect-specified?**
   **Resolution**: KEEP all 5 sections per architect §3.7.B. The validator does not enforce `## Metrics targets` but architect §3.7.C #1 says "EVERY file MUST have these 5 H2 sections in this order". Architect doc is canonical for content; validator is canonical for the *minimum* enforced subset. Implementers MUST include `## Metrics targets` even though the validator won't fail without it — it's reviewer-enforced (5.2.9 spec-compliance) and serves Phase 5.5's measurement needs.

3. **Q: Brief says "≥3 failure modes" but architect §3.7.C #3 says "≥1 item". Which?**
   **Resolution**: ≥3 per the brief. The brief is more recent (this dispatch), and architect §3.7.C #3 is a floor not a ceiling ("at least 1"). Tightening to ≥3 matches the discipline of `## Assertions` (≥3) and gives Phase 5.5 measurable failure-mode coverage. Reviewer 5.2.9 enforces.

4. **Q: Implementer prompt size — should we inline each SKILL.md content into the prompt, or just point at the file path?**
   **Resolution**: Point at the file path. Implementers read SKILL.md as Step 1 (~5K tokens for the largest one). Inlining bloats the prompt and defeats the fresh-context property of MULTI_TASK_IMPL. Per-skill task table in this plan pre-digests the trigger/failure-mode content so the implementer has a baseline even before reading SKILL.md.

5. **Q: Idempotency on re-dispatch — what if a `.test.md` file already exists from a partial prior run?**
   **Resolution**: Per architect §3.7.G: implementer MUST detect existing file BEFORE writing. If conformant (validator passes) → SKIP, return `DONE_WITH_CONCERNS, concern: pre-existing-file-confirmed-conformant`. If non-conformant → return `BLOCKED` (do NOT silently overwrite). Defends Mode E (pre-staged work).

6. **Q: Does the finalizer dispatch's edit to `tests/scripts/skills-validate.spec.ts` Case #9 risk colliding with prior Case #7 edits from 5.2.7?**
   **Resolution**: NO. 5.2.7 already flipped Case #7 (visible at lines 105–113 of the current spec). 5.2.7's flip is the model; 5.2.8's flip mirrors it on Case #9 (lines 129–137). The two cases are disjoint test bodies with different fixture roots (`missing-allowed-tools-root` vs `missing-test-root`). No edit collision.

7. **Q: Risk: the `prisma-sqlite` skill's `.test.md` will reference patterns in `*.repository.ts` files that DON'T YET EXIST (5.3 territory).**
   **Resolution**: Acceptable. The assertions are forward-looking — they say "every `*.repository.ts` MUST have pattern X". Until 5.3 lands, the grep returns ZERO files, which is vacuously true (the assertion `every X has Y` is satisfied when X is empty). When 5.3 lands and adds repositories, the pre-existing `.test.md` becomes an active gate. This is the design intent (test-first).

8. **Risk: `pnpm -r test` baseline (≥1387) might shift between 5.2.7 close and 5.2.8 finalizer due to other parallel work.**
