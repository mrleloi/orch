## Empirical Pre-Findings (drive the design)

These are observed from live data before designing — they are the load-bearing facts:

**F1.** `agent-workspace/memory/component-telemetry.jsonl` contains 190 `trigger:"agent_dispatch"` rows; **all** carry `component_name:"unknown-agent"`. Zero rows with `component_name:"Task"` (i.e. PostToolUse on Task tool). This means the only place the `agent` bucket is being populated is `SubagentStop`, NOT `PostToolUse(tool_name=Task)`.

**F2.** `component-telemetry.sh::classify_component()` for `SubagentStop` reads `(p.tool_input && p.tool_input.subagent_type) || ''` from the payload. Empirical evidence (190 rows of `unknown-agent`) shows that the **SubagentStop hook payload does not carry `tool_input.subagent_type`** in real Claude Code emissions — `subagent_type` is only present in the **PreToolUse** payload for `tool_name="Task"`. Fallback to `unknown-agent` is therefore deterministic, not anomalous.

**F3.** `agent-workspace/memory/dispatch.jsonl` contains 1 DISPATCHED row (`toolu_smoke_01`, a synthetic smoke test) and 98 COMPLETED rows. COMPLETED rows have `dispatch_id` values like `aaa80398aa10d20b8` — 16-char hex strings sourced from `payload.agent_id` at SubagentStop. DISPATCHED rows would have `dispatch_id="toolu_*"` from `payload.tool_use_id` at PreToolUse-Task. **The two ID spaces do not overlap empirically** because PreToolUse-Task is NOT firing for real dispatches — only the smoke test's synthetic emit produced a DISPATCHED row.

**F4.** Decision 026 §"v2.3 Fix-List Item" already pre-bounded the design space: do a `cat /dev/stdin > /tmp/pretooluse-$(date +%s).json` diagnostic probe **before locking** any field choice, because Root Cause A (timing) vs Root Cause B (missing field) cannot be distinguished without empirical capture.

**F5.** `Agent` tool spawn is **in-process** in the parent Claude Code TUI, not a `claude --rc` subprocess. Therefore env-var injection from the orch daemon to "spawned agents" only applies to the `session-handoff.sh` use case (a fresh top-level session). For Task-tool subagents (the 190 we care about), the seam is purely the parent's hook chain — there is no separate process to inject env vars into.

**Implication of F5**: The "named-agent self-reporting" requirement (Decision 034 prereq #2) is misnamed. The fix is not "spawned agents emit a component_name". The fix is **"the parent's SubagentStop hook recovers the subagent_type from a sidecar populated at PreToolUse-Task in the same parent session"**. This is the same structural seam as CF-21. Both prerequisite gates collapse onto a single fix: **populate a sidecar at PreToolUse-Task indexed by `tool_use_id`, then read it at SubagentStop indexed by `agent_id`** — provided `tool_use_id` and `agent_id` denote the same Task invocation.

**F6 (load-bearing risk).** The H2 test in `tests/hooks/dispatch-recorder.spec.ts:157-193` PASSES today by emitting matching `tool_use_id` and `agent_id` values in synthetic payloads. This proves the sidecar code path works WHEN the IDs match. The empirical 0.00 pairing rate proves they do NOT match for real Claude Code emissions. The architect cannot pre-verify which of three sub-cases obtains without the diagnostic probe (see Sub-Task A.0 below):
   - Case α — `tool_use_id` is missing entirely from PreToolUse-Task stdin (Decision 026 Root Cause B). Fix: alternative correlation key.
   - Case β — `tool_use_id` is present at PreToolUse-Task as `toolu_*`, AND SubagentStop's `agent_id` is the SAME `toolu_*` value. Fix: nothing structural — the H2 test path is correct, the only bug is that PreToolUse-Task never fires (Decision 026 Root Cause A; self-heals on next reload).
   - Case γ — `tool_use_id` is present as `toolu_*`, but SubagentStop's `agent_id` is a DIFFERENT canonical value (hex digest of subagent process ID, etc.). Fix: emit BOTH ids at PreToolUse-Task into the sidecar so SubagentStop can match on either.

The design below assumes **Case γ** as the safe default (emit both keys), and the diagnostic probe at Sub-Task A.0 ratifies which case is real. The IMPL design is robust to all three cases.

## Cross-Cutting Design Decisions (D&R log)

### D1. Single sidecar file vs two

**Chosen**: ONE sidecar file (`.dispatch-pending-<session>.jsonl`), two readers (`dispatch-jsonl-recorder.sh` for COMPLETED enrichment, `component-telemetry.sh` for SubagentStop classification). Reason: avoids schema duplication and ensures the two seams agree on which subagent_type was bound to which dispatch. Atomic POSIX append-only invariant preserved.

### D2. `tool_use_id` in DISPATCHED schema (Decision 023 schema lock)

**Chosen**: ADDITIVE — add `tool_use_id` as a 10th field. Decision 023 §"schema is locked" is interpreted as forbidding **field removal/rename**, not additive evolution. Confirmed by reading Decision 023's intent (consumer compatibility). All existing 9 fields stay byte-identical.

### D3. Diagnostic probe vs design assumption

**Chosen**: Mandatory probe (Sub-Task A) BEFORE locking sidecar key strategy. Reason: the cost of a 20K probe is dwarfed by the cost of a wrong-key landing that 10.5.3's gate-3 measurement reveals as still 0.00. Decision 026 explicitly anticipated this and pre-authorized the probe.

### D4. Named-agent fix scope

**Chosen**: Implement at the parent's SubagentStop hook (sidecar lookup), NOT at the spawned-agent's SessionStart (env-var injection). Reason: F5 above — Task-tool subagents are in-process; there is no separate SessionStart event for them. The orch-daemon-spawned `claude --rc` case (which DOES have its own SessionStart) is out of scope for SC-39 prerequisites; those sessions emit their own component_name independently.

### D5. Schema strict mode

`ComponentEventSchema` in `packages/core/src/telemetry/component-telemetry.schema.ts` uses `.strict()` — additive fields would FAIL parsing. **Action item for Sub-Task C**: do NOT add new fields to ComponentEventSchema; the named-agent recovery rewrites `component_name` only. ComponentEventSchema is unchanged.

For the dispatch JSONL, there is currently no Zod schema in `packages/core/src/dispatch/` (file does not exist per phase 9.5 observation). The schema is documented-only in Decision 023. Adding `tool_use_id` is therefore safe; consumers (`loadTaskFinishRecordsFromDispatchJsonl`) parse with `JSON.parse` and ignore unknown fields.

## Risks (architect-acknowledged, escalation-tagged)

**R1 — Diagnostic probe outcome unknown.** Sub-Task A may reveal Case α (no `tool_use_id` in PreToolUse stdin), forcing the description-hash fallback. This degrades correlation precision (collision risk on identical task descriptions). Mitigation: B's schema absorbs both cases; the H9 / pairing-rate harness asserts ≥ 0.40 pairing on the chosen key, NOT necessarily 1.00. The 0.40 threshold gives 60% slack — sufficient for description-hash to land if substring uniqueness holds over a phase cycle.

**R2 — `tool_use_id` ↔ `agent_id` are different ID spaces (Case γ).** If empirical, B's sidecar stores both keys, and SubagentStop tries `agent_id` first then `tool_use_id` then description-hash. This adds 2 lookup paths (≤6 LOC). Acceptable.

**R3 — PreToolUse-Task hook still does not fire (Decision 026 Root Cause A unresolved).** This is a settings.json reload-timing artifact that self-heals on next session restart. If the probe (Sub-Task A) reveals zero `.diag-pretooluse/*.json` files after a confirmed Task dispatch, this is the real cause; fix is "do nothing structural; restart session and re-probe". A 10.5.2.A `escalation.md` would be authored noting "structural seam is correct; PreToolUse-Task fires after restart; Decision 026 §"v2.3 Fix-List" item 2 self-heal verified".

**R4 — `agent` rows may also originate from `PostToolUse(tool_name=Task)` after the fix.** Per F1, currently zero such rows exist; once Claude Code wiring health is restored (R3 self-heal), these rows MAY start appearing. They will already carry `subagent_type` natively in `tool_input`, so the existing `classify_component` PostToolUse branch handles them correctly with no code change. Cross-check: B and C must not break that branch.

**R5 — Test-fixture credibility.** The integration test in C-B.2 uses synthetic emits; it does not exercise the live Claude Code hook chain. The "real" measurement happens at 10.5.3 against post-merge live telemetry. Mitigation: 10.5.3 explicitly waits ≥ 1 phase cycle of dogfooding before measuring (Decision 034 prereq #3 — phase-cycle stability).

**R6 — ComponentEventSchema strict mode.** If anyone adds a `tool_use_id` or `subagent_type` field to component-telemetry rows (Sub-Task C), schema parsing will FAIL. **Hard rule**: C must rewrite `component_name` only; no new fields. Reviewer (code-quality) must confirm.

**R7 — Schema drift between dispatch.jsonl and ComponentEventSchema.** dispatch.jsonl has its own Decision-023 schema (no Zod). component-telemetry.jsonl has Zod-strict ComponentEventSchema. The two schemas evolve independently. This is OK because they serve different consumers; a future task may consolidate but is out of scope.
