### Q2 — Where does substage attribution come from?

**Critical input-feasibility finding**: `agent-workspace/memory/component-telemetry.jsonl`
records 3,217 events but `task_id` is **`null`** in ALL of them (verified by
`grep -c '"task_id":null'` ≈ 3214/3217). Neither does `subagent-index.md` carry per-task
attribution (column shows "unknown"). Therefore raw telemetry CANNOT be grouped by
substage directly.

**Resolution**: derive substage wallclock from the **session-log filename pattern**
`agent-workspace/memory/sessions/2026-04-27-task-6.<S>.<N>-*.md` (where `<S>` ∈ {1,2,3}
identifies the substage). For each task-id, take its session-log file's filesystem
mtime as `task_end_ts`. For `task_start_ts`, use the **previous** task's `task_end_ts`
within the same substage (or the substage's first-task arrival time = file ctime/mtime
of the first 6.<S>.<N> log).

This is the same mechanism `subagent-index.md` already uses (`return_ts` from the
hooks log, `start_ts` "n/a"), so it's a known-degraded but workable proxy.

A simpler **alternative** (and recommended primary path for 6.4.2): use the per-task
session log's **literal mtime** as `task_finish_ts`, treat each substage as a contiguous
window `[min(task_finish_ts) - duration_proxy, max(task_finish_ts)]`, and compute:

- `wallclock_actual` = `max(task_finish_ts) - min(task_finish_ts)` for the substage
- `wallclock_serial_baseline` = `sum(task_duration_proxy)` where each task's
  `duration_proxy` is the gap between consecutive sorted task-mtimes within the
  substage (with the FIRST task's duration set to a fixed convention — see Q4).

### Q3 — Fixture for empty-input + single-substage spec cases (Part B's `tests/benchmarks/sc18-realworld.spec.ts`)?

**In-memory fabrication.** The spec MUST NOT touch the real
`agent-workspace/memory/sessions/` directory (writing to a real fixture risks polluting
v2.1.0 staged state). Instead, the spec passes a **fixture array of `{taskId, finishTs}`
objects** directly into a pure exported function `computeSubstageImprovement(tasks)`,
asserting the math. The CLI entry point (`main()`) does the filesystem read; tests
exercise the math via the pure function.

### Q4 — How to handle the FIRST task in each substage (no preceding task to bound its duration)?

Convention: the substage's **first** task has `duration_proxy` = the first-to-second
task gap (i.e., copy the second task's gap). This avoids zero-padding (which would
collapse `serial_baseline → wallclock_actual` and produce 0% improvement spurious
PASS). Spec test T2 (single-substage with 3 tasks) explicitly asserts this convention.

### Q5 — Single-file dominant chunk in 6.3 (6.3.4 adapter, 130K, single-file = forced serial)?

It contributes to **both** `wallclock_actual` AND `wallclock_serial_baseline` equally
(it's a serial component within a parallel substage). The 6.3 substage as a whole
still admits parallelism on its other tasks (6.3.5 || 6.3.6, 6.3.2 || 6.3.3). The
formula naturally accounts for this — the substage's measured improvement is
mechanically capped by the dominant single-file chunk, and that cap is what
master plan §4 estimates at ~30%.

Public API (test-import surface):

```typescript
export interface TaskFinishRecord {
  taskId: string;        // e.g. "6.1.2", "6.2.5"
  substage: '6.1' | '6.2' | '6.3';
  finishTs: number;      // ms epoch (filesystem mtime)
}

export interface SubstageResult {
  substage: '6.1' | '6.2' | '6.3';
  taskCount: number;
  wallclockActualMs: number;
  wallclockSerialBaselineMs: number;
  improvementRatio: number;     // 1 - (actual / serial); range [0..1] expected
  passesThreshold: boolean;     // improvementRatio >= 0.35
}

export interface SC18RealWorldReport {
  generatedAt: string;          // ISO-8601 UTC
  sessionsScanned: number;
  substages: SubstageResult[];
  passingSubstageCount: number;
  sc27Verdict: 'PASS' | 'PARTIAL' | 'FAIL';  // PASS = ≥2; PARTIAL = 1; FAIL = 0
  thresholdImprovement: 0.35;
  thresholdSubstageCount: 2;
}

/** Pure function — used by spec tests directly. */
export function computeSubstageImprovement(
  tasks: TaskFinishRecord[],
): Omit<SubstageResult, 'substage'> & { substage: TaskFinishRecord['substage'] };

/** Pure function — aggregate per-substage results into final report. */
export function buildReport(records: TaskFinishRecord[]): SC18RealWorldReport;

/** Filesystem boundary — only invoked from CLI main(), never from tests. */
export async function loadTaskFinishRecords(
  sessionsDir: string,
): Promise<TaskFinishRecord[]>;

/** Markdown emitter — pure, takes the report, returns string. */
export function renderMarkdown(report: SC18RealWorldReport): string;

/** CLI entry. */
async function main(): Promise<void>;
```

CLI invocation: `pnpm tsx scripts/benchmarks/sc18-realworld.ts`. Optional flags
`--sessions-dir <path>` and `--output <path>`. Defaults:
- `--sessions-dir`: `agent-workspace/memory/sessions/`
- `--output`: `agent-workspace/memory/sc18-realworld-result.md`

`loadTaskFinishRecords(sessionsDir)` algorithm:
1. Read directory entries; filter to filenames matching
   `/^2026-04-27-task-(6\.(1|2|3))\.(\d+)[a-z]?-.*\.md$/` (note: 6.3.8a/8b are kept).
2. For each match, capture `substage` (group 1) and `taskId` (group 1 + . + group 3).
3. `fs.stat(path).mtime.getTime()` → `finishTs` (ms epoch).
4. Return sorted by `finishTs` asc.

`computeSubstageImprovement(tasks)` algorithm (per substage; tasks pre-filtered to one
substage):
1. Sort `tasks` ascending by `finishTs`.
2. If `tasks.length === 0` → return `{ taskCount:0, wallclockActualMs:0,
   wallclockSerialBaselineMs:0, improvementRatio:0, passesThreshold:false, substage }`.
3. If `tasks.length === 1` → `wallclockActualMs = 0`,
   `wallclockSerialBaselineMs = 0`, `improvementRatio = 0`, `passesThreshold = false`
   (insufficient data; one-task substage cannot be parallelized).
4. Otherwise:
   - `wallclockActualMs = tasks[n-1].finishTs - tasks[0].finishTs`.
   - `durations[i] = tasks[i].finishTs - tasks[i-1].finishTs` for i ∈ [1..n-1].
   - `durations[0] = durations[1]` (the first-task convention from §2 Q4).
   - `wallclockSerialBaselineMs = sum(durations)`.
   - `improvementRatio = wallclockSerialBaselineMs > 0
       ? 1 - (wallclockActualMs / wallclockSerialBaselineMs) : 0`.
   - **Note**: with the convention above, `wallclockSerialBaselineMs ===
     wallclockActualMs + durations[0] === wallclockActualMs + durations[1]`. So the
     improvement is `durations[1] / wallclockSerialBaselineMs`. Math stays well-formed
     and bounded in [0, 1) for n ≥ 2.

`buildReport(records)` aggregates into the 3 substages (6.1, 6.2, 6.3) explicitly,
emits the SC-27 verdict by counting `passesThreshold === true`.

it('emits SC_27 PASS when 2-of-3 substages clear ≥35% threshold', () => {
  // Engineer 6.1 to 50%, 6.2 to 40%, 6.3 to 25% — expect PASS (2 of 3).
  // 6.1: tasks at [0, 100, 200, 300, 400] → durations [_, 100, 100, 100, 100],
  //   first-dup → [100, 100, 100, 100, 100]; wallclockActual = 400;
  //   wallclockSerial = 500; improvement = 20% — too low.
  // To get 50% need: actual = serial / 2.  With dup-first convention, that means
  //   actual = 4*g, serial = 5*g; ratio = 4/5 → 20% always for uniform spacing.
  // Therefore non-uniform: tasks [0, 50, 100, 1000]. wallclockActual=1000,
  //   durations[0]=50 (dup of duration[1]=50); serial = 50+50+50+900 = 1050;
  //   improvement = 1 - 1000/1050 ≈ 4.8%. Wrong direction.
  //
  // Realization: with this convention, parallelism shows when EARLY tasks finish
  // CLOSE to the start (i.e., they ran concurrently); a late lone tail task makes
  // wallclockActual ≈ wallclockSerial (low parallelism). 6.1's expected ~50%
  // empirically arises because the 3 IMPL tasks (6.1.2/6.1.3/6.1.4) finished
  // within seconds of each other after 6.1.1, and 6.1.5 wrapped quickly. So the
  // T3 fixture must mimic that: cluster tasks tightly except for the last spread.
  //
  // 6.1 fixture (target ≥35%):
  //   tasks at [0, 10, 20, 30, 1000]. wallclockActual = 1000.
  //   durations[1..4] = [10, 10, 10, 970]; durations[0]=10. serial = 1010.
  //   improvement = 1 - 1000/1010 ≈ 1%. Still wrong direction.
  //
  // CORRECT INTUITION: with the chosen formula, wallclockSerialBaseline is just
  // wallclockActual + durations[0] (the duplicated first gap). So
  //   improvement = durations[0] / serial = durations[0] / (actual + durations[0]).
  // For improvement ≥ 35%, need durations[0] ≥ 0.35 * serial, i.e.
  //   durations[1] (which equals durations[0]) >= 0.35 * (actual + durations[1]),
  //   i.e. 0.65 * durations[1] >= 0.35 * actual,
  //   i.e. durations[1] >= (0.35/0.65) * actual ≈ 0.538 * actual.
  // So if FIRST gap is large relative to the rest, improvement is high.
  // E.g., tasks at [0, 1000, 1100, 1200] → actual = 1200, durations[1..3] = [1000,
  //   100, 100]; durations[0] = 1000 (dup); serial = 2200; improvement = 1000/2200
  //   ≈ 45.5%. PASS.
  //
  // So semantics: a LARGE first gap == "tasks started together (parallel) so the
  // first observed finish is far into the substage; subsequent close finishes
  // mean parallelism." This is correct: in a parallel substage, the FIRST task to
  // finish takes the full single-task time; subsequent tasks finish soon after,
  // so the trailing gaps are small.
  const tasks: TaskFinishRecord[] = [

    { taskId: '6.1.1', substage: '6.1', finishTs: 0 },
    { taskId: '6.1.2', substage: '6.1', finishTs: 1000 },
    { taskId: '6.1.3', substage: '6.1', finishTs: 1100 },
