## §6. Risks

### Risk 1 — Push site placement ambiguity (LOW)

**Risk**: `tests/hooks/api-truncation.spec.ts` has 6 `it()` blocks. Only 2 currently assert `durationMs`. The implementer might over-eagerly add pushes to all 6 (harmless but increases LOC) or under-add (only at the assertion sites, missing other call sites where `durationMs` is computed but not asserted).

**Mitigation**: Part-B B.2 explicitly says "push at BOTH sites where the assertion was". Implementer follows the existing surface, not a generalized rule. Verifier P5 enforces LOC budget; over-eager pushes would inflate net additions and trigger budget gate.

### Risk 2 — Reporter line printed multiple times due to test isolation (LOW)

**Risk**: Vitest may run tests in worker threads with separate module loads, causing the module-scope accumulator to reset between `it()` blocks. The reporter would then print only the last-run-block's duration count, not the aggregate.

**Mitigation**: This is exactly the shape `tests/hooks/tool-call-first.spec.ts` uses successfully (with `lintDurations` accumulating across 6 `it()` blocks). The reference is proven; if vitest config in this repo isolates differently, the reference would already be broken, which it isn't. Verifier P1 checks reporter output captures n>1; if n=1 always, that's a config issue worth flagging — but unlikely.

### Risk 3 — Implementer attempts to "improve" by adding fake timers anyway (MEDIUM)

**Risk**: The Phase 6 §F retrospective text labels the fix `vi.useFakeTimers + advanceTimersByTime`. An implementer reading §F directly (skipping Decision 022) might believe useFakeTimers IS the canonical pattern and add it.

**Mitigation**:
- Decision 022 is binding and explicitly rejects useFakeTimers with named rationale.
- Architect dispatch context (Part A "Dispatch context" block) repeats the prohibition verbatim.
- Verifier P2 asserts `grep -E "useFakeTimers"` = 0 across `tests/hooks/`. Any addition fails verification.
- Architect spec §1 and §2 reiterate the rejection.

### Risk 4 — Carryforward #20 stall during 7.1.2 (LOW)

**Risk**: 7.1.2 modifies 2 files with combined ~25-40 LOC delta. If the IMPL stalls mid-edit (e.g., between editing api-truncation and starting narration-grep), partial changes are recoverable from `git diff` but the IMPL session must restart cleanly.

**Mitigation**: 7.1.2 is sized at 80K — well below carryforward #20's 200K threshold. Each file edit is independent (no cross-file references). If a stall occurs after api-truncation but before narration-grep, the partial state is staged via `git add` per Mandate B, and a continuation IMPL can pick up narration-grep alone.

### Risk 5 — Verifier P3 false positive (process.platform baseline) (LOW)

**Risk**: 7.1.4 P3 caps `process.platform` count at 2. If the IMPL inadvertently adds a comment containing the word `process.platform` (e.g., in a docstring), the gate would fire.

**Mitigation**: The current 2 matches are both in actual code, not comments. The IMPL spec's "Forbidden additions" rule applies to ALL `process.platform` text including comments. Verifier P3 reading is binary: does count > 2? If yes, the IMPL must rephrase the comment.
