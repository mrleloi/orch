## §2 Option Selection — Option D (`FIX_INLINE_MINIMAL` + `RUN_CONTROL_FLAG`)

### §2.1 Decision

**Selected: Option D** from `cf-dogfood-2-assessment.md` §3.4
(FIX_INLINE_MINIMAL + RUN_CONTROL_FLAG, ~90 LOC). Option B-minimal (§3.2,
~80 LOC, no flag) is **rejected** for the reasons in §2.3.

### §2.2 Why Option D (Karpathy-grounded rationale)

1. **P2 simplicity (minimum delta to satisfy G3)** — Option D adds exactly
   one env-var check (`process.env.ORCH_DOGFOOD_EXECUTE === 'true'`) plus an
   `if/else` branch around the existing step-9 trace block. The flag-OFF
   branch is the existing code path verbatim (preserving the 11 unit tests
   T1–T11 that currently pass). The flag-ON branch is ~50 LOC of
   `try { spawn → drain streams → awaitAndClassify } catch { translate to
   exit code }`. Total delta: ~90 LOC. No new modules, no new interfaces,
   no schema changes.

2. **Runtime safety (the critical decider)** — Without a flag, every dogfood
   smoke test in CI would attempt to invoke `ccs <profile>` (the `ccs` CLI
   subprocess), which on most CI runners (a) is not installed and (b) if
   installed would consume the user's API quota. Option B-minimal (no flag)
   means: the moment 12.1 lands, the 1512-test suite tries to execute real
   `claude --rc` calls against a CI environment that lacks the binary. This
   is an unacceptable regression of test determinism.

3. **Charter coherence — Decision 031 telemetry-sync precedent** — Decision
   031 establishes the "default-OFF, opt-in via env-var" pattern for
   side-effecting features (telemetry sync). The dogfood real-spawn path is
   structurally identical (side-effecting on opt-in; observable behaviour
   when ON; quiet stub when OFF). Adopting the same idiom keeps
   developer mental-model consistent.

4. **G4 unblocking (12.3)** — 12.3 substage requires an explicit
   `ORCH_DOGFOOD_EXECUTE=true` invocation to fire the real spawn. Without
   the flag, 12.3 has no kill-switch — any orchestrator-side mistake during
   smoke verification of the wired harness would burn user tokens. With the
   flag, 12.3 gates the real-execute behind an explicit env-var the operator
   sets only at the dispatch moment.

5. **Backward compatibility (T9 stub-mode tests pass without modification)**
   — The existing T1–T11 tests in `tests/dogfood/run-self-task.spec.ts`
   (1512 tests total in the suite, of which ~12 touch the harness directly)
   never set `ORCH_DOGFOOD_EXECUTE`. Default is OFF → flag-OFF branch runs →
   existing assertions on the stub trace shape stay valid. No retrofit
   needed.

### §2.3 Why Option B-minimal is rejected

Option B-minimal (§3.2 of the assessment doc, ~80 LOC, no flag) saves 10 LOC
relative to Option D. The savings are not worth the cost:

- **Test determinism regression**: as noted in §2.2 point 2, every test
  that exercises the harness path becomes a real subprocess call. Vitest
  cannot reliably mock this at the `execa` boundary because the harness
  imports `IAgentRuntime` directly via `@orch/core`; mocking that module
  surface is fragile (vitest auto-mock vs explicit `vi.mock` discipline).
- **CI quota leak risk**: a developer running `pnpm test` locally with `ccs`
  authenticated could accidentally fire 1+ real `claude --rc` invocations
  per test run. Even one such accident is unacceptable.
- **No kill-switch for 12.3**: the operator has no way to dry-run the
  end-to-end harness in 12.3 without committing to a real spawn. Option D's
  flag-OFF gives a free dry-run.
- **No "phased rollout" path**: with no flag, there is no way for 12.4+
  substages to choose stub-mode for early-development reasons. Option D's
  flag is a small, ongoing affordance that costs ~10 LOC to keep around.

### §2.4 Why neither Option A, C, nor E

- **Option A (FIX_INLINE_FULL)**: out-of-scope for 12.1 per master plan
  (envelope authoring is 12.3's job; running C2 + C3 is also 12.3's job).
- **Option C (DEFER_V2.6)**: superseded by Decision 040 — defer is no longer
  permitted; G3 is mandatory in v2.7.
- **Option E (RESOLVED_BY_DOCUMENTATION)**: superseded by Decision 040
  §3 priority inversion — the user_prompt.txt §1.5 mandate ("phase 8 trở đi
  nên thực sự được tiếp cận bằng cách dùng chính dự án này") explicitly
  requires the harness to **work**, not just to be documented as
  scaffold-shaped.

### §3.3 B.2 — `IAgentRuntime.spawn()` call envelope (dependency injection)

**Signature change for `runSelfTask`**:

```ts

// Post-fix:
export async function runSelfTask(
  envelopePath: string,
  runtime?: IAgentRuntime,  // optional; defaults via factory when undefined
```

**Default-runtime factory** (only invoked when flag is ON AND no runtime
injected by caller):

```ts
async function defaultRuntime(): Promise<IAgentRuntime> {
  // Lazy import: do not pull NestJS dependencies into the harness top-level.
  const { ClaudeCodeAdapter } = await import(
    '../../packages/core/src/modules/sessions/claude-code-adapter.js'
  );
  const { TracingService } = await import(
    '../../packages/core/src/modules/tracing/tracing.service.js'
  );
  return new ClaudeCodeAdapter(new TracingService());
}
```

**Why optional injection + default factory**:
- Tests inject a `vi.fn()`-shaped mock that satisfies the `IAgentRuntime`
  interface (T13–T15 below) — no real `ClaudeCodeAdapter` instantiation.
- Production CLI (`cliMain()`) calls `runSelfTask(envelopePath)` with no
  runtime arg → default factory is hit → real `ClaudeCodeAdapter`.
- Lazy `await import()` keeps the harness's module-load cost the same as
  today when flag is OFF (no `@nestjs/common` import in the cold path).

**`dispatchViaRuntime()` shape**:

```ts
async function dispatchViaRuntime(
  runtimeOrUndef: IAgentRuntime | undefined,
  envelope: DogfoodEnvelope,
  fullPrompt: string,
  childEnv: NodeJS.ProcessEnv,
  tracePath: string,
  log: (msg: string) => void,
): Promise<void> {
  const runtime = runtimeOrUndef ?? (await defaultRuntime());

  // Map envelope.subagent_type → ccs profile name. For 12.1 default policy,
  // use envelope.tenancy.user as the profile (e.g., 'self', 'orch-daemon').
  // Future: profile mapping can move to envelope.metadata.ccs_profile.
  const profile = (envelope.metadata?.['ccs_profile'] as string | undefined)
    ?? 'default';

  let handle: RuntimeHandle;
  try {
    handle = await runtime.spawn({
      profile,
      prompt: fullPrompt,
      env: childEnv as Record<string, string>,
    });
  } catch (err) {
    log(`runtime-spawn-failed: ${err instanceof Error ? err.message : String(err)}`);
    appendTrace(tracePath, {
      spanName: 'dogfood.subprocess_spawn',
      attrs: {
        subagent_type: envelope.subagent_type,
        model: envelope.model,
        effort: envelope.effort,
        budget_cap_tokens: envelope.budget_cap_tokens,
        prompt_length: fullPrompt.length,
        spawn_error: err instanceof Error ? err.message : String(err),
      },
      timestamp: new Date().toISOString(),
      status: 'error',
    });
    throw err;  // propagate to outer catch in runSelfTask → SPAWN_FAILED
  }

  log(`runtime-spawned pid=${handle.pid} sessionId=${handle.sessionId || '(pending)'}`);

  // Stream drain — log lines, do not buffer (memory-bounded by adapter).
  handle.stdout.on('data', (chunk: Buffer) => {
    log(`stdout: ${chunk.toString('utf8').slice(0, 200)}`);
  });
  handle.stderr.on('data', (chunk: Buffer) => {
    log(`stderr: ${chunk.toString('utf8').slice(0, 200)}`);
  });

  // Emit "spawn started" trace BEFORE awaiting completion (so that a hang on
  // awaitAndClassify is observable via the JSONL tail).
  appendTrace(tracePath, {
    spanName: 'dogfood.subprocess_spawn',
    attrs: {
      subagent_type: envelope.subagent_type,
      model: envelope.model,
      effort: envelope.effort,
      budget_cap_tokens: envelope.budget_cap_tokens,
      prompt_length: fullPrompt.length,
      pid: handle.pid,
      session_id: handle.sessionId || '',
      flag_off: false,
    },
    timestamp: new Date().toISOString(),
  });

  // Await child exit + classify non-zero exits as typed DomainErrors.
  await runtime.awaitAndClassify(handle);
  log(`runtime-completed pid=${handle.pid}`);
}
```

### §3.4 B.3 — Profile flag wiring (env-var; default OFF for safety)

**Default behavior (flag absent OR not exactly `'true'`)**: the harness
emits a `dogfood.subprocess_spawn` trace record with `flag_off: true` and
returns from the step-9 closure without invoking `IAgentRuntime.spawn()`.
The trace shape preserves the 5 attributes the existing assertions check
(`subagent_type`, `model`, `effort`, `budget_cap_tokens`, `prompt_length`)
plus the new `flag_off` attribute.

**Why exactly `=== 'true'`** (not `Boolean(...)` or `parseInt(...)`):
- `Boolean('false')` returns `true` (non-empty string is truthy) — error-
  prone. Strict equality with the literal `'true'` is unambiguous.
- Aligns with the pattern used in `claude-code-adapter.ts` for
  `ORCH_DOGFOOD_PARENT_OK === '1'` (strict literal compare).

**Forbidden** (do not implement): `profile.yaml`-based flag, `.orch/`-based
flag, or any persisted-on-disk flag. The flag MUST be transient
process-environment-only — operator sets it explicitly at invocation:
`ORCH_DOGFOOD_EXECUTE=true pnpm dogfood:run-self-task <envelope>`.

### §3.5 B.4 — Error handling (subprocess crash, rate-limit, timeout)

The `dispatchViaRuntime()` helper (B.2) covers three error classes:

| Error class | Source | Handling |
|---|---|---|
| Spawn failure (binary not found, profile unknown) | `runtime.spawn()` throws `RuntimeSpawnError` | catch → appendTrace `status: error` + `spawn_error` field → re-throw → outer catch in `runSelfTask` (lines 414–423) maps to `EXIT_CODES.SPAWN_FAILED` (= 4) |
| Non-zero exit (rate limit, context full, auth) | `runtime.awaitAndClassify()` throws typed `DomainError` subclass | re-thrown by helper → outer catch in `runSelfTask` maps to `EXIT_CODES.SPAWN_FAILED` (= 4); error message is preserved in `appendTrace` `error:` field via the existing outer-catch trace emission (lines 416–423 of current file) |
| Timeout / hang | not handled in 12.1 | **Out-of-scope**; phase-13 candidate (`RetryWatchdog` integration). 12.1 relies on `awaitAndClassify` to resolve naturally. If the subprocess hangs forever, the harness hangs forever — operator kills it. This is an acceptable v2.7 limitation per Decision 040 §"runtime safety" (the flag is default OFF; the operator opts in knowing real spawns can hang). |

**No new `EXIT_CODES`** — the existing `SPAWN_FAILED` (= 4) covers both
spawn-side and post-spawn classification failures. This matches the
fail-classification matrix in spec §4.3 and avoids schema churn.

## §6 Risks (≥ 4)

### §6.1 R-12.1.1 — Subprocess hang in real-execute path (HIGH)

**Description**: Once flag is ON, `runtime.awaitAndClassify(handle)` waits
for child exit. If `claude --rc` hangs (e.g., waiting on a TTY input that
never arrives because stdin was not allocated), the harness hangs forever.

**Mitigation**:
- Default flag OFF (12.1 ships dormant; this risk only fires when 12.3+
  explicitly opts in).
- 12.3 substage MUST set a wall-clock budget on the dogfood invocation
  (e.g., `timeout 600 pnpm dogfood:run-self-task ...`).
- Phase 13 candidate: `RetryWatchdog` integration to enforce
  envelope-supplied wall-clock + token budget.

**Acceptance**: documented in Risks §6.1 of this spec; 12.3 substage
inherits the constraint via master plan §12.3 acceptance gate
("housekeeping task chosen for 12.3 is closed with concrete diff
evidence" implies the dispatch must complete).

### §6.2 R-12.1.2 — `ccs` CLI not on PATH (MEDIUM)

**Description**: The default `ClaudeCodeAdapter` factory calls
`execa('ccs', ...)`. On CI runners (GitHub Actions) and on developer
machines without `ccs` installed, this throws `ENOENT` synchronously,
which is caught and wrapped as `RuntimeSpawnError`.

**Mitigation**:
- Default flag OFF prevents this from firing unless explicitly opted in.
- Test T14 covers the `RuntimeSpawnError` propagation path via the
  injected mock runtime — no real `ccs` invocation in CI.
- 12.3 substage MUST be invoked on a developer machine where `ccs` is
  authenticated; CI MUST NOT set `ORCH_DOGFOOD_EXECUTE=true`.

### §6.3 R-12.1.3 — Profile flag accidentally ON in CI (HIGH)

**Description**: A misconfigured CI workflow could export
`ORCH_DOGFOOD_EXECUTE=true` (e.g., copy-pasted from local `.env` file),
causing every `pnpm test` run to attempt real `claude --rc` spawns.

**Mitigation**:
- Test T13 explicitly sets and unsets the env-var per-test and asserts
  on `mockRuntime.spawn` invocation count — leaks via `process.env` are
  caught by `afterEach(() => process.env = savedEnv)`.
- Document in `agent-workspace/memory/observations/task-12.1-20260428-impl.md`
  that no CI workflow sets this var.
- Reviewer pair MUST grep `.github/workflows/` for `ORCH_DOGFOOD_EXECUTE`
  during code-quality review and fail PR if any workflow sets it
  unconditionally.

### §6.4 R-12.1.4 — Rate-limit failover unwired (LOW)

**Description**: When `awaitAndClassify` throws `RateLimitError`, the
harness exits with code 4 (`SPAWN_FAILED`) and emits an error trace. It
does NOT re-route to a different `ccs` profile, schedule retry, or
escalate. This is intentional 12.1 scope.

**Mitigation**:
- Test T15 covers the `RateLimitError` exit path — the harness's behavior
  is documented and tested.
- Deferred to Phase 13 candidate: `RetryWatchdog` integration with
  `IAgentRuntime`.
- 12.3 substage acceptance gate (master plan §12.3) only requires ≥ 1
  successful trace; rate-limit failure is a re-runnable condition.

### §6.5 R-12.1.5 — Test mock surface drift (MEDIUM)

**Description**: T13–T15 mock the `IAgentRuntime` interface fully. If the
interface gains a new method in a future phase (e.g., `pause()` for
suspended-resume), the mocks fail TypeScript compilation.

**Mitigation**:
- All 5 current `IAgentRuntime` methods (`spawn`, `resume`, `terminate`,
  `awaitAndClassify`, `writeStdin`) are mocked in each test (verified via
  the test code in §3.7).
- A future interface extension forces the test mocks to be updated — this
  is desired (compile-time tripwire).

## §8 Forbidden Patterns

The following patterns MUST NOT appear in the 12.1 implementation. Each
is a hard reject by reviewer pair / verifier:

1. **No direct `child_process.exec` / `spawn` in `run-self-task.ts`** —
   all subprocess invocation MUST flow through `IAgentRuntime.spawn()`.
   The harness imports `IAgentRuntime` (interface) only; the concrete
   `ClaudeCodeAdapter` is created via the lazy factory `defaultRuntime()`.
   Rationale: I-3 (CLI-only path) + I-14 (handle stays domain-pure).

2. **No synchronous `spawnSync`** — the dispatch path MUST be `await`-able.
   The existing `runtime.spawn()` is async; `awaitAndClassify` is async.
   Synchronous spawn would block the OTEL `tracer.withSpan` callback and
   corrupt span timing.

3. **No API-key leak in trace** — the trace records §3.6 MUST NOT include
   environment-variable contents (`process.env`), credential headers, or
   any field that could carry an API key. The whitelist of attrs allowed
   in the spawn trace is exactly the 6–8 fields enumerated in §3.6
   (`subagent_type`, `model`, `effort`, `budget_cap_tokens`,
   `prompt_length`, `pid`, `session_id`, `flag_off`).

4. **No `git commit` during 12.1** — I-6 ABSOLUTE. Reviewer pair confirms
   gate C.9 (`git log` baseline unchanged).

5. **No `profile.yaml` schema change** — the `ORCH_DOGFOOD_EXECUTE` flag
   is process-env-only. Adding a `dogfood.execute: true` field to
   `profile.yaml` would (a) persist the opt-in across daemon restarts
   (footgun) and (b) require a Tier-2 schema migration spec.

6. **No new `EXIT_CODES`** — reuse `SPAWN_FAILED` (= 4) for all
   spawn-side and post-spawn classification failures. Adding a new
   `RATE_LIMITED` code requires a Tier-2 spec change.

7. **No new top-level dependencies** — no new `package.json` deps; no
   new dev-deps. The fix uses `IAgentRuntime` (already exported from
   `@orch/core`), `RuntimeHandle` (already exported), and Node built-in
   stream types. The tracer / `TracingService` is already imported.

8. **No removal of existing T1–T11 tests** — all 11 existing tests in
   `tests/dogfood/run-self-task.spec.ts` MUST continue to pass under
   flag-OFF default. T12–T15 are additive, not replacements.

9. **No `eslint-disable` comments** — the new code MUST comply with the
   existing eslint config without disable directives. If a rule fires,
   refactor — do not silence.

10. **No `// @ts-ignore` / `// @ts-expect-error`** — strict TypeScript.
    If a type does not check, fix the type — do not bypass.
