## Part A — Context & Rationale

### A.1 Why this task exists

Phase 3 implementation tasks (3.0–3.10) each have unit + module-integration coverage. Charter F4 (force-handoff at 230K threshold path) and the daemon's autonomous hand-off chain are now individually green, but the chain of `OTEL span ingestion → ContextBudgetService threshold → session.force-handoff event → SessionManager._handleForceHandoff → graceful stdin write → session.ended → HandoffOrchestrator → DB persist → adapter.spawn(seedPrompt)` has never been exercised in one suite with the real Nest DI graph + real Prisma SQLite. Task 3.11 is that integration.

## Part C — Tests

Each `it()` block specifies: name, what it asserts, setup, teardown. **Total: 7 it() blocks** (5 mandated + 1 cron + 1 regression guard) → monorepo target ≥ 1326 (1319 + 7).

### C.1 `it()` block specifications

#### `A1: synthetic spans crossing warn threshold emit session.context-near-limit`

- **Asserts**: After firing synthetic spans whose cumulative `gen_ai.usage.input_tokens` first crosses `warnAtTokens: 800` (e.g. spans of [400, 401] → total 801), a `session.context-near-limit` event fires exactly once with `{ sessionKey, projectId, currentTokens: 801, threshold: 800 }`.
- **Setup**: Listener registered via `eventBus.on(EVENT_CHANNELS.session.contextNearLimit, ...)` BEFORE the spans fire (proven-safe pattern, latency.spec.ts:478). Promise that resolves on first event.
- **Act**: `fireSyntheticSpan(tracer, sessionKey, projectId, 400)` then `fireSyntheticSpan(tracer, sessionKey, projectId, 401)`.
- **Assert**: Promise resolves; payload field-by-field check.
- **Teardown**: unsubscribe listener (the helper from `eventBus.on` returns the unsub fn).

#### `A2: synthetic spans crossing force threshold emit session.force-handoff`

- **Asserts**: After firing one more synthetic span (e.g. 200 tokens, total 1001), a `session.force-handoff` event fires exactly once with `{ sessionKey, projectId, currentTokens: 1001, threshold: 1000 }`. Order matters: must arrive AFTER the A1 near-limit event.
- **Setup**: Continuation of A1's session-key (same suite-level state, same sessionKey). Listener registered before the act-step.
- **Act**: `fireSyntheticSpan(tracer, sessionKey, projectId, 200)`.
- **Assert**: Promise resolves; payload check; assert via captured array that `near-limit` came first.
- **Teardown**: unsub.

#### `A3: SessionManager invokes adapter.writeStdin with /session-end\n`

- **Asserts**: When `session.force-handoff` is emitted with a sessionKey that IS in `SessionManager.active`, `_handleGracefulEnd` calls `adapter.writeStdin(handle, '/session-end\n')`. Verify `fakeAdapter.stdinWrites` contains exactly one entry whose `text === '/session-end\n'` for the active session's `handleId`.
- **Setup pre-requisite (load-bearing — if not solvable, SPLIT)**: SessionManager's `active` Map is private and is populated only via `runSession() → executeSession()`. TWO PATHS to choose between (sandwich-dev MUST pick one and document the choice in the session log):
    - **Path A (preferred — closer to production)**: Call `sessionManager.runSession(projectId, plan)` and let it spawn the fake handle, registering active state. Because the fake adapter's stdout `.end()`s on `process.nextTick`, executeSession's `_awaitHandleCompletion` resolves quickly. Trigger force-handoff DURING the active window — i.e. fire the synthetic spans IMMEDIATELY after the spawn returns, before the stdout drain completes. This requires keeping the fake `stdout` open until A3 has fired its assertion. Implement by holding the `PassThrough` open until the test signals via a flag, then `.end()` it after the stdin-write assertion.
    - **Path B (fallback — surgical access)**: Use `(sessionManager as unknown as { active: Map<string, ActiveSessionState> }).active.set(...)` to inject a fake `ActiveSessionState` directly. Document this as a deliberate test-only coupling. Includes the active-map private-field-access pattern that ContextBudgetService already uses against ProjectRegistryService internals (cited at `context-budget.service.ts:282-292`).
- **Recommendation**: Try Path A first; fall back to Path B with a clear `// E2E test-only coupling: see plan §C.1 A3` comment if Path A is too brittle.
- **Act**: Emit one final synthetic span pushing total past 1000 (or directly emit `eventBus.emit(EVENT_CHANNELS.session.forceHandoff, payload)` if going Path B with a manually-injected active state).
- **Assert**: `fakeAdapter.stdinWrites.length` >= 1; entry has `text === '/session-end\n'`.
- **Teardown**: tear down active state (Path A: let executeSession finish naturally; Path B: delete from map).

#### `A4: HandoffContext row persisted via Path B (post-commit transaction)`

- **Asserts**: After A3's graceful-end completes and emits `session.ended` with `endReason = ContextFull` (or `ContextFullForced` if timeout), HandoffOrchestrator subscribes, builds the context, and writes a `HandoffContext` row. Verify via `prisma.handoffContext.findFirst({ where: { fromSessionId: <sessionId> } })`. Assert the row exists, has `seedPrompt` populated (non-empty), and `status` ∈ `{'READY_FOR_AUTO_SPAWN', 'APPLIED'}`.
- **Setup**: Listener on `session.handoffPrepared` to await persist completion (proven-safe Promise pattern). The handoff is async (`_handleContextFullEnd` is `async`), so the test must await this signal explicitly.
- **Act**: continuation of A3 — no new act needed; the chain runs autonomously.
- **Assert**: Prisma query against tmpdir SQLite returns the row. Decision 007 path B → assert this is a SEPARATE row created AFTER `session.ended` was already emitted by checking the `handoffPrepared` event was the LAST one in the chain before the spawn (best-effort ordering check).
- **Teardown**: nothing (rows persist for A5).

#### `A5: successor session spawned with rendered seedPrompt in SpawnConfig`

- **Asserts**: After A4, `fakeAdapter.spawnConfigs` has at least 2 entries (the original session + the successor). The latest spawn config has:
    - `seedPrompt` field present and non-empty.
    - `seedPrompt` contains substring markers that prove it's a rendered handoff template (e.g. contains `'## Pickup point'` OR `'CONTEXT_FULL'` OR a string from the actual `prompt-renderer.ts` template — sandwich-dev should `Read` `prompt-renderer.ts` to identify a stable substring).

- **Teardown**: nothing.

## Part F — Risks / SCOPE-DISCARD / SPLIT items

### F.1 R-A3 — Active-map population for graceful-end test

**Risk**: SessionManager's `active` Map is populated only inside `executeSession()`. To get `_handleForceHandoff` to find the session, EITHER we run a real `runSession()` OR we inject the active state via private-field access.
**Mitigation**: Attempt Path A first; document the choice. If Path A fails after one honest attempt, switch to Path B and add an explicit comment citing the precedent (`context-budget.service.ts:282-292` already uses private-field access against ProjectRegistryService internals — same pattern).
**SPLIT trigger**: if BOTH paths produce flakes (>1 failure in 5 consecutive runs), STOP and SPLIT — the integration cannot be done deterministically without a SessionManager refactor, which is out of scope.

### F.2 R-cron-fake-time — Scheduler + Prisma tx + fake timers incompatibility

**Risk**: jest fake timers + Prisma transaction timeout (5000 ms via setTimeout) → fake-clock advance causes immediate transaction expiry. Documented in `scheduler.integration.spec.ts:18-23`.
**Mitigation**: USE REAL TIMERS + 6-field every-second cron `* * * * * *` + 3 s deadline poll. Plan §C.1 B1 specifies this approach explicitly. NO `jest.useFakeTimers()` anywhere in the spec.
**SPLIT trigger**: if the cron path is flaky on Windows due to clock-skew (>2 failures in 5 runs), reduce assertion to "within 10s" (still satisfies the plan requirement that the cron triggers the enqueue path) and document the deviation.

### F.3 R-synthetic-span-flow — In-memory tracer wiring

**Risk**: synthetic spans fired via `tracer.startSpan().end()` may not flow through `ContextBudgetSpanProcessor` if the test forgets to `addSpanProcessor()`.
**Mitigation**: E4 adds an explicit smoke check that proves the wiring works before committing to A1.
**SPLIT trigger**: if `ContextBudgetService.snapshot()` returns undefined after a fired span, this is a wiring bug — FIX in test, do NOT touch production code (since `context-budget.integration.spec.ts:48-101` proves the production code path works).

### F.4 R-handoff-template-substring — Brittle string match in A5/R1

**Risk**: PromptRenderer template may evolve; A5 substring assertion may break.
**Mitigation**: Pick a STABLE substring (a section header that's been in the template since 3.5). Document the chosen substring + line number in a top-level constant comment.
**Mitigation alt**: assert STRUCTURAL fields on the deserialized `contextJson` (e.g. `git.startCommit`, `nextPickup`) rather than scanning the rendered text. This is more stable. R1 already does this; consider doing the same in A5.

### F.5 R-stdout-stream-timing — Fake handle stdout drain too fast

**Risk**: If the fake adapter's stdout `.end()`s on `process.nextTick` (round-trip pattern), `_awaitHandleCompletion` resolves before A3 can fire its synthetic spans → SessionManager `active` map is cleared before `_handleForceHandoff` runs.
**Mitigation**: Use a controllable `PassThrough` whose `.end()` is called only after A3 has captured its assertion. Or fall back to Path B (direct active-map injection) where stream timing is irrelevant.
**SPLIT trigger**: not applicable — this is a timing knob the test owns.

### F.6 R-handoff-id-not-correlated — Multi-handoff confusion

**Risk**: A4 queries `prisma.handoffContext.findFirst()` without filtering by `fromSessionId`. If a previous test polluted state, the wrong row could match.
**Mitigation**: Always filter by `fromSessionId` from the active session record. Use unique sessionKeys per scenario.

### F.7 R-budget-overrun — Plan estimates 120K; complex multi-system suite

**Risk**: Suite complexity may push real consumption past 120K; sandwich-dev should monitor.
**Mitigation**: §E shows ~95K budget with 25K headroom. If sandwich-dev hits 110K and is not on E10, STOP and write a checkpoint + escalate.
**SPLIT trigger**: if E6 (Scenario A) alone exceeds 60K, dispatch E7 (cron) as a separate sandwich-dev session. The two scenarios are decoupled.

### F.8 SCOPE-DISCARDED items

- Rendered-prompt content correctness (covered by 3.5 unit tests on `prompt-renderer.spec.ts`).
- Real `git rev-parse HEAD` in handoff (Path A defers — R1 pins the placeholder).
- Real session log file path tracking (Path A defers — null in seed).
- Telegram notification path on session.handoffPending (covered by `packages/telegram` tests; out of scope per round-trip.spec.ts R3 precedent).

### F.9 STOP conditions
