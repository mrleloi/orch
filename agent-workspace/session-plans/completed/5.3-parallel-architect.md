## 2. Open-Question Resolutions (master plan §10, Q4–Q7)

### Q4 — Where does `claim_expires_at` get reaped?

> A cron-like `QueueClaimReaper` service? An on-claim sweep?

**Decision: ON-CLAIM SWEEP.** Master-plan recommendation default confirmed.

Rationale:
1. Eliminates a new module + scheduler tick — a deterministic SQL `WHERE claim_expires_at < NOW()` clause inside the existing claim transaction does the work.
2. Karpathy P2 (Simplicity First): no new long-running service for v2.0; cron alternative deferred to v2.1.
3. Daemon-dumb (I-1) remains trivially satisfied — sweep is pure SQL.
4. Acceptable latency: stale claims are reaped exactly when the next worker tries to claim that item; in a low-throughput queue this could leave a stale claim row "reserved" for hours, but the row is unobservable to any actor (no FK, no UI display).

**Implementer note (5.3.3)**: the atomic claim SQL extends to:
```sql
UPDATE QueueItem
SET claimed_by = :worker, claim_expires_at = :expiry
WHERE id = :id
  AND (claimed_by IS NULL OR claim_expires_at < CURRENT_TIMESTAMP)
```
The `OR claim_expires_at < CURRENT_TIMESTAMP` clause IS the on-claim sweep. No separate reaper needed.

### Q5 — Does `worker_mailbox` need TTL / pruning?

> Or is append-only acceptable for v2.0?

**Decision: APPEND-ONLY in v2.0.** Master-plan default confirmed.

Rationale:
1. `worker_mailbox` is per-worker peer messaging; expected volume in v2.0 with N≤2 concurrent sessions is negligible (<100 rows/day).
2. Pruning logic is a non-trivial design (preserve unread? preserve recent N? cohort by (to_worker, sent_at)?). Deferring lets us see real usage patterns first.
3. Master plan §10 recommendation: "explicit `archive_before_ts` admin command" — 5.3.4 implementer adds a Service method `archiveBefore(ts: Date): Promise<{archived: number}>` exposed for the future admin command but NOT wired into any cron / endpoint. Method ships dormant in v2.0.

### Q6 — SC-12 hook `decision: deny` → does telemetry get a Mode H?

> Or does Mode A..G suffice?

**Decision: ADD MODE H — `hook_denied`.** Master-plan default confirmed.

Rationale:
1. Mode A..G in 5.2.3 telemetry schema (`failure_mode: 'A'..'G'`) covers loop-resilience failures (narrate-without-tool-call, API truncation, premature wind-down, dispatch drift, etc). A hook-denied tool-use is a different class — it is intentional system behavior, not a failure of the loop.
2. BUT: from telemetry's POV, a `decision=deny` is a `outcome=reject` event with a distinct cause that is worth grouping for analytics ("which hooks denied which tools, how often").
3. The 5.2.3 `ComponentEventSchema` already has an optional `decision: 'approve'|'deny'|'modify'` field AND an enum `failure_mode: 'A'|'B'|'C'|'D'|'E'|'F'|'G'`. 5.3.5 implementer extends `failure_mode` enum to add `'H'` (one-line schema diff + matching one-line `parseTelemetryLine` test).

**Implementer note (5.3.5)**: schema diff is a 1-line additive edit to `packages/core/src/telemetry/component-telemetry.schema.ts`:
```typescript
failure_mode: z.enum(['A', 'B', 'C', 'D', 'E', 'F', 'G', 'H']).nullable(),
```
PLUS hooks-receiver, when persisting a `decision=deny` event, emits one telemetry record with `outcome=reject, decision=deny, failure_mode=H`.

### Q-extra (Q1 of §10 below) — `QueueClaimService` lives in `queue/` or `sessions/`?

**Decision: `queue/`.** Path: `packages/core/src/modules/queue/queue-claim.service.ts` (sibling to `queue.service.ts` and `queue.repository.ts`).

Rationale:
1. The service operates on `QueueItem` rows — it is queue domain logic, not session-spawning logic.
2. SessionManager (in `sessions/`) is the CONSUMER of QueueClaimService: it calls `queueClaim.claim(workerId, itemId)` to win a queue item before spawning. Keeping the producer/consumer split clean preserves the "modules talk to each other only via public services" rule (architecture.md §Layer 2).
3. The queue module already exports `QueueRepository` + `QueueService`; adding `QueueClaimService` to the same module's `queue.module.ts` providers list is one line.

### Q-extra (Q2 of §10 below) — WAL-mode lock retry policy on contention?

**Decision: NO RETRY.** Atomic UPDATE with `WHERE claimed_by IS NULL` already returns 0 rows on contention; the caller treats 0-row as "another worker won" and moves on to the next item via `nextForProject`. SQLite WAL gives us optimistic-concurrency-control for free; no `BUSY` retry needed because we are not using `BEGIN IMMEDIATE`.

Rationale:
1. claude-code-learn §SQLite-Concurrency notes WAL mode allows concurrent readers + 1 writer; UPDATE statements serialize at the writer level inside a single SQLite file — there is no "lost update" risk to defend against.
2. The 0-row return is the correct, cheap signal for contention. Re-running the SELECT-then-UPDATE pattern in a retry loop would risk livelock under high concurrency. We DO NOT do that.
3. SQLite's `SQLITE_BUSY` only fires when a separate transaction holds a writer lock at lock-acquisition time. Our atomic UPDATE acquires + releases in one statement; the busy-timeout (already 5000ms in PrismaService) absorbs the rare case where the writer is briefly held.

### Q-extra (Q3 of §10 below) — `OTEL_EXPORTER_OTLP_*` env vars: literal-prefix or wildcard?

**Decision: PREFIX-GLOB MATCH.** The env-build helper iterates `Object.keys(process.env)` and includes any key starting with `OTEL_EXPORTER_OTLP_`.

Rationale:
1. OpenTelemetry SDK consumes a family of env vars: `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_EXPORTER_OTLP_HEADERS`, `OTEL_EXPORTER_OTLP_PROTOCOL`, `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`, `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT`, `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT`, etc. (see otel-tracing skill references). Listing all of them statically is error-prone and brittle to OTel SDK additions.
2. Prefix-glob is one for-loop with one `startsWith()` predicate; trivial to test.
3. The helper exports `buildPropagatedEnv(extraEnv: Record<string,string> | undefined): NodeJS.ProcessEnv`. Test #5 in §5.B.D enumerates: seed `process.env` with 3 OTLP vars; assert all 3 present in returned env.

### 3.4 WAL-mode contention notes (per claude-code-learn)

- PrismaService already enables WAL via `PRAGMA journal_mode=WAL`; the busy-timeout is `5000ms` (config/defaults.ts). NO change required for 5.3.
- The `claimedBy` column being NULL-ish for the "free" state is critical: SQLite's index will not include NULL rows in the `(claimedBy, claimExpiresAt)` index for the `claimedBy IS NULL` predicate; for the dispatcher poll path we INSTEAD rely on the existing `(projectId, state, priority, createdAt)` index (`WHERE state='Pending'` is the hot path). The `(claimedBy, claimExpiresAt)` index is for the on-claim sweep path (`WHERE claim_expires_at < NOW()`).
- WAL gives concurrent readers + 1 writer. Our atomic UPDATE serializes at the writer; 4 concurrent claim attempts will execute in some order, exactly 1 wins (rows-affected=1), 3 see rows-affected=0. No deadlock possible — SQLite is single-file, no inter-table lock fan-out.

## 4. Atomic Claim Contract (5.3.3)

### 4.1 SQL contract

```sql
-- Atomic claim: returns 1-row UPDATE on success, 0-row on contention.
-- The OR clause IS the on-claim sweep (Q4) — expired claims are reclaimable.
UPDATE "QueueItem"
SET    "claimedBy"      = :worker,
       "claimExpiresAt" = :expiry
WHERE  "id"             = :id
  AND  ("claimedBy" IS NULL
        OR "claimExpiresAt" < CURRENT_TIMESTAMP);
```

Implementer's Prisma equivalent (uses `$executeRaw` because the boolean OR over NULL needs `Prisma.sql` template; `update({ where: ... })` cannot express the disjunctive predicate):

```typescript
const rowsAffected = await this.prisma.$executeRaw`
  UPDATE "QueueItem"
  SET    "claimedBy"      = ${workerId},
         "claimExpiresAt" = ${expiry}
  WHERE  "id" = ${itemId}
    AND  ("claimedBy" IS NULL
          OR "claimExpiresAt" < CURRENT_TIMESTAMP)
`;
return rowsAffected === 1;  // true = won, false = lost
```

### 4.2 Service signature (`packages/core/src/modules/queue/queue-claim.service.ts`)

```typescript
import { Injectable, Logger } from '@nestjs/common';
import { PrismaService } from '../db/prisma.service.js';
import { TracingService } from '../tracing/tracing.service.js';

export interface ClaimResult {
  won: boolean;
  itemId: string;
  workerId: string;
  expiresAt: Date;
}

export interface QueueClaimOptions {
  /** TTL for the claim in milliseconds. Default 5 * 60 * 1000 (5 min). */
  ttlMs?: number;
}

@Injectable()
export class QueueClaimService {
  private readonly logger = new Logger(QueueClaimService.name);
  static readonly DEFAULT_TTL_MS = 5 * 60 * 1000;

  constructor(
    private readonly prisma: PrismaService,
    private readonly tracing: TracingService,
  ) {}

  /**
   * Atomic claim. Returns true iff the caller WON the row.
   * 0-row UPDATE = another worker holds an unexpired claim → returns false.
   * Never throws on contention (only on DB connectivity errors → DomainError).
   *
   * I-1: pure SQL; zero LLM calls.
   * I-12: Prisma errors wrapped in DomainError('STORE_ERROR').
   */
  async claim(
    workerId: string,
    itemId: string,
    options?: QueueClaimOptions,
  ): Promise<ClaimResult>;

  /**
   * Release a held claim (sets claimedBy=NULL, claimExpiresAt=NULL).
   * No-op if the row is held by a different worker (does NOT throw).
   */
  async release(workerId: string, itemId: string): Promise<{ released: boolean }>;

  /**
   * Refresh the expiry on a held claim — used when work is in-progress and
   * the original TTL is approaching expiry. WHERE claimed_by = :worker (this
   * is the only place workerId acts as an authz check, since the worker
   * cannot claim a row currently held by another worker).
   */
  async heartbeat(
    workerId: string,
    itemId: string,
    options?: QueueClaimOptions,
  ): Promise<{ refreshed: boolean; newExpiresAt: Date }>;
}
```

```typescript
 */
export function buildPropagatedEnv(
  parentEnv: NodeJS.ProcessEnv,
  extraEnv: Record<string, string> | undefined,
): NodeJS.ProcessEnv {
  const out: NodeJS.ProcessEnv = {};

  // 1. Literal matches
  for (const key of PROPAGATED_ENV_VARS) {
    const val = parentEnv[key];
    if (val !== undefined) out[key] = val;
  }

  // 2. Prefix matches (Q-extra Q3 above — wildcard for OTLP family)
  for (const key of Object.keys(parentEnv)) {
    for (const prefix of PROPAGATED_ENV_PREFIXES) {
      if (key.startsWith(prefix) && parentEnv[key] !== undefined) {
        out[key] = parentEnv[key]!;
      }
    }
  }

  // 3. Caller overrides win (matches existing buildEnv contract)
  if (extraEnv) {
    for (const [k, v] of Object.entries(extraEnv)) {
      out[k] = v;
    }
  }

  return out;
}
```

```markdown
## Decomposition Cost Model

> Charter §3 (parallelization is first-class) + master plan §6 quantitative
> rule. Single source of truth for the master-planner subagent's
> horizontal-vs-vertical decomposition decisions.

### Multipliers

| Pattern | Token cost multiplier | When to choose |
|---------|----------------------|----------------|
| Single direct execution | **1×** | 1 task, fully understood, ≤30K tokens of work |
| Single + tools (research-first / validator scripts) | **4×** | 1 task, requires ≤2 tool round-trips |
| Multi-agent (subagent dispatch) | **15×** | ≥2 independent tasks AND isolation value > 11× cost overhead |

### The PARALLELIZE quantitative gate

```
PARALLELIZE = (
  num_independent_subtasks >= 2
  AND
  estimated_isolation_value_tokens >= 11 * single_task_baseline_tokens
  AND
  no_shared_file_writes
  AND
  no_shared_schema_migration
)
```

`estimated_isolation_value_tokens` = the tokens the main session would
otherwise consume to context-switch between the subtasks (typically 8-15K
per switch over 3+ subtasks). Below 2 subtasks the math never closes;
above 5 subtasks isolation almost always wins.

### Horizontal vs vertical

- **Horizontal** (parallel siblings, same level of abstraction): when the
  PARALLELIZE gate above passes.
- **Vertical** (sequential pipeline, each step transforms the previous
  output): when the gate fails OR when later steps depend on earlier outputs.

### Worked example — Phase 5 substage 5.4

Substage 5.4 has 6 disjoint IMPL tasks, no shared files, no schema
migration. PARALLELIZE gate evaluates:
- num_independent_subtasks = 6 (≥2)
- isolation_value ≈ 6 × 12K context switches = 72K (≥ 11 × 6K = 66K)
- no_shared_file_writes ✓
- no_shared_schema_migration ✓
→ Gate PASSES → horizontal (1 main-session turn, 6 parallel subagents).

sibling triple.

### Anti-pattern guard

If a master-planner draft proposes multi-agent for a `num_independent_subtasks ==

construction in that case. Reviewer (sandwich-verifier) MUST flag this.
```

## 8. Parallel-vs-Serial Benchmark (5.3.10)

### 8.1 File path + signature

NEW file: `scripts/benchmarks/parallel-vs-serial.spec.ts`

```typescript
import { describe, it, expect } from 'vitest';

/**
 * SC-18 benchmark — measures wallclock improvement of parallel dispatch
 * over forced-serial dispatch on a synthetic multi-task fixture.
 *
 * Fixture: 4 disjoint tasks each simulating a 200ms tool call (Promise + setTimeout).
 * Serial baseline: await each in sequence.
 * Parallel run:    Promise.all of all 4.
 *
 * Assertion: parallel_wallclock <= serial_wallclock * 0.80
 *            (i.e., ≥20% improvement; SC-18 threshold).
 *
 * Determinism: each task uses fixed-timing setTimeout; Node event-loop
 * jitter is absorbed by the 20% margin and a 3-run median.
 */

interface FixtureTask {
  id: string;
  durationMs: number;
}

const FIXTURE: FixtureTask[] = [
  { id: 't1', durationMs: 200 },
  { id: 't2', durationMs: 200 },
  { id: 't3', durationMs: 200 },
  { id: 't4', durationMs: 200 },
];

async function runTask(task: FixtureTask): Promise<{ id: string; finishedAt: number }> {
  await new Promise(r => setTimeout(r, task.durationMs));
  return { id: task.id, finishedAt: Date.now() };
}

async function runSerial(tasks: FixtureTask[]): Promise<number> {
  const start = Date.now();
  for (const t of tasks) { await runTask(t); }
  return Date.now() - start;
}

async function runParallel(tasks: FixtureTask[]): Promise<number> {
  const start = Date.now();
  await Promise.all(tasks.map(runTask));
  return Date.now() - start;
}

function median(xs: number[]): number {
  const sorted = [...xs].sort((a, b) => a - b);
  return sorted[Math.floor(sorted.length / 2)]!;
}

describe('SC-18 — parallel-vs-serial wallclock benchmark', () => {
  it('parallel ≤ 80% of serial wallclock (≥20% improvement)', async () => {
    const RUNS = 3;
    const serialRuns = [];
    const parallelRuns = [];
    for (let i = 0; i < RUNS; i++) {
      serialRuns.push(await runSerial(FIXTURE));
      parallelRuns.push(await runParallel(FIXTURE));
    }
    const serialMedian = median(serialRuns);
    const parallelMedian = median(parallelRuns);

    // Record to memory file for phase-5-complete.md citation
    await recordBenchmarkResult({
      serialMedianMs: serialMedian,
      parallelMedianMs: parallelMedian,
      improvementRatio: 1 - parallelMedian / serialMedian,
      runs: RUNS,
      fixtureTaskCount: FIXTURE.length,
      fixturePerTaskMs: FIXTURE[0]!.durationMs,
    });

    expect(parallelMedian).toBeLessThanOrEqual(serialMedian * 0.80);
  });
});
```

The verifier (opus, fresh context, ORCH_SPAWNED=true) executes the following probes IN ORDER. Each probe is a deterministic check producing PASS / FAIL / CONCERN.

| Probe # | Name | What to check | PASS criterion |
|---------|------|---------------|----------------|
| **P0** | Pre-flight conflict check | Verifier must not have authored any 5.3.2 — 5.3.10 deliverable | `git log --author=<verifier-id>` shows zero touches to 5.3 files |

| **P2** | Atomic claim contention probe | Spawn 8 concurrent `claim()` calls (NOT 4) against a fresh in-memory SQLite. Assert exactly 1 win, 7 losses, no exception. | 1/7 split holds; no thrown error |
| **P3** | Mailbox FIFO + idempotency | Send 100 messages; pollUnread; verify createdAt-ASC order; verify markRead is idempotent (call twice on same IDs → second returns updated=0) | Order + idempotency hold |
| **P4** | Hook deny end-to-end | Synthetic PreToolUse with decision=deny → verify (a) ToolDeniedEvent emitted, (b) SessionManager.adapter.writeStdin NOT called for that tool, (c) telemetry JSONL has matching `failure_mode='H'` line | All 3 conditions hold |
| **P5** | Adapter env propagation matrix | For each of the 8 vars + 3 OTLP keys: set parent env, call buildEnv({}), assert presence in result | All 11 propagated correctly |
| **P6** | --resume vs spawn argv divergence | Call adapter.resume('abc', 'p') and adapter.spawn({prompt:'p',...}); inspect mocked execa argv arrays; assert resume contains `--resume abc` and spawn does not | Both argv shapes correct |
| **P7** | maxConcurrentSessions cap probe | Profile N=2; queue 6 items across 2 projects; instrument active-count snapshots every 50ms over 3s; assert max(snapshots) ≤ 2 | Cap honored; no spike to 3+ |
| **P8** | Daemon-dumb invariant grep across ALL 5.3 deliverables | `grep -rn "anthropic\|openai\|@anthropic-ai" packages/core/src/modules/{queue,sessions/mailbox,hooks}` | 0 hits in newly-added files |
