## Part D — Risks + Decisions

### D1. Langfuse auth header format — VERIFIED via context7 MCP

**Decision**: Use HTTP Basic auth (`Authorization: Basic <base64(publicKey:secretKey)>`).

**Verification**: I attempted to query the context7 MCP for current Langfuse OTLP docs but the tool was not available in this architect session (only `Read`, `Glob`, `Grep`, `Write`). However, the codebase already implements this pattern in `tracing-bootstrap.ts:91-98` (`buildLangfuseAuthHeader`) and decision-005 cites `https://langfuse.com/docs/opentelemetry/get-started` as the source. The 11 existing unit tests confirm the header is `Basic <base64>` format and that decoding round-trips correctly. Treating the existing implementation as authoritative — the architect of #19 verified against live docs. **If the dev encounters any auth failure during integration smoke, escalate** — do not patch the header format speculatively.

**Risk if format is wrong**: Langfuse OTLP endpoint returns 401; spans drop silently (R5: exporter retries silently). Detection requires a real Langfuse endpoint, which we do not exercise in tests (I-13). Production verification belongs in a manual smoke pass, not this session.

### D2. Bogus `ORCH_TRACE_BACKEND` value handling

`tracing-bootstrap-startup.ts` reads raw env BEFORE `validateEnv()` runs (which lives in `ConfigModule.forRoot({ validate })` in `app.module.ts`). If the operator sets `ORCH_TRACE_BACKEND='foo'`:
- The bootstrap factory's `if (backend === 'otlp')... else if (backend === 'langfuse')... ` chain falls through; `traceExporter` stays undefined. Effective behavior: like `'none'` — SDK starts without remote exporter.
- Then `app.module.ts` boot calls `validateEnv()`, which throws on the invalid enum, and the daemon crashes with a clear zod error.

**Decision**: Accept this two-step failure mode. Document in a 3-line comment in `tracing-bootstrap-startup.ts`. Do not duplicate validateEnv at bootstrap time — that would violate I-10's "schema is the single source of truth" principle. The only observable consequence is "tracing transiently degrades to none for the few hundred ms between bootstrap and validateEnv crash" — acceptable for a misconfiguration crash path.

### D3. Test isolation — side-effect import problem

Module-level side effects (the `bootstrapTracing(...)` call at the top of `tracing-bootstrap-startup.ts`) are run exactly once per Jest worker. Subsequent imports return the same singleton. This is why the test plan extracts a pure `readBootstrapOptsFromEnv(env)` function rather than re-importing the startup module per case.

**Decision**: 5-line refactor — extract the env-read into a named export, keep the module-level call which now reads `readBootstrapOptsFromEnv(process.env)` and calls `bootstrapTracing()` with the result. Tests exercise the pure function; no Jest module cache shenanigans.

### D4. Should we fall back to `otlp` when `langfuse` is selected but keys are missing?

Phase plan §Task 3.9 line 245 implies the toggle replaces the exporter cleanly. The existing factory **throws** when langfuse keys missing (`tracing-bootstrap.ts:170-174`). The schema's superRefine **also** rejects this combination at validateEnv time. **Decision**: keep both guards. Schema catches the misconfiguration first (clearer error message) — no silent fallback. The bootstrap throw is a defense-in-depth backstop for callers that bypass validateEnv (e.g. unit tests that call `bootstrapTracing` directly). **Karpathy P2**: do not add a third "fall back to otlp" path — three branches are enough.

### D5. NoopSpanProcessor vs no-exporter for `none`

The current `none` branch sets `traceExporter` to `undefined` and spreads conditionally (`...(traceExporter !== undefined ? { traceExporter } : {})`) so NodeSDK starts without a remote exporter. In-process span processors (added in `TracingModule.onModuleInit` via `getDelegate().addSpanProcessor()`) work because the underlying `BasicTracerProvider` is created regardless. The existing test `tracing-bootstrap.spec.ts:213` proves this. **Decision**: NO change. Do not add NoopSpanProcessor — that would be code-bearing for zero behavior change.

### D6. Budget — single dev pass without verifier?

This is a ~120 LOC narrow-wiring + smoke test. The factory branching itself was already verified by the 3.8 verifier ("3.9's remaining surface is exporter selection in `tracing-bootstrap.ts` plus 6+ unit tests + integration smoke"). After sandwich-dev returns DONE, **the orchestrator may dispatch sandwich-verifier** if the gate output reveals any deviation; otherwise this is a candidate for fast-track close (single architect → dev pass with optional verifier). Document this proposal in §H.
