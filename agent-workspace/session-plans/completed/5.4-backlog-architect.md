### 5.4.9 — Mailbox markRead Count-Idempotency (CF-1)

**Part A (context):**
The 5.3.12 verifier probe P3 found that `mailbox.repository.ts:151` uses
`updateMany({ where: { id: { in: ids } } })` without a `read: false` filter. This means a
second call to `markRead(ids)` returns `count > 0` even though no rows changed state
(the rows were already read). This is "state-idempotent but not count-idempotent." The
verifier recommended: either add `read: false` filter (count-idempotent fix) or document
state-idempotent semantics in `MailboxService` docstring as canonical contract. This task
implements the count-idempotent fix (cleaner) and adds a test case proving it.

**Part B (contract):**
- Files to modify:

### 5.4.10 — Document Hook-Deny Daemon Log-Only Design (CF-2)

**Part A (context):**
The 5.3.12 verifier probe P4 found that `session-manager.ts`'s `_handleToolDenied` method
only logs + emits an OTEL span event when a hook returns `{decision: "deny"}`. The daemon
does NOT add a parallel `writeStdin`-suppression gate because the Claude CLI permission model
is the upstream gate. This is a deliberate architectural choice, but it is not documented
anywhere in the architecture constitution or in the hooks service header. Future readers may
re-ask the question or (worse) add an incorrect writeStdin suppression. This task adds a
1-paragraph explanation in `architecture.md §Layer 3` or the hooks service file header.

**Part B (contract):**
- Files to modify:

    the Layer 3 (Hooks) section explaining: daemon receives `{decision: "deny"}`, emits
    `ToolDenied` domain event, logs the message; it does NOT invoke `writeStdin` suppression
    because the Claude CLI permission model is the upstream enforcement gate; daemon's role
    is to observe and record, not duplicate the CLI gate
  - `packages/core/src/modules/hooks/hooks.service.ts` (or `session-manager.ts` — locate
    the `_handleToolDenied` handler) — add a 3–5 line docstring above the handler explaining
    the same design rationale
