## Goal
Implement a deterministic, per-session context-budget detector that:
1. Observes per-span `gen_ai.usage.input_tokens` (already populated by Claude Code's native OTEL emission per I-15).
2. Maintains a per-session running token total in memory.
3. Emits `session.context-near-limit` exactly once when the warn threshold is crossed.
4. Emits `session.force-handoff` exactly once when the force threshold is crossed.
5. Reads thresholds from the project profile (`context_budget` block) with defaults (warn=200,000; force=230,000) tied to charter F4.
6. Propagates both events through SSE so Telegram + Web UI receive them.

Charter goal: **F4** — `PROJECT_CHARTER.md:83`:
> "When OTEL span reports tokens > 230K, Orch gracefully ends current session and spawns next with handoff context."

Charter Principle 1: **`PROJECT_CHARTER.md:53`** — daemon-dumb. ContextBudgetService is pure deterministic code, NO LLM calls.
Charter Principle 10: **`PROJECT_CHARTER.md:71`** — no agent-intelligence creep into core.

## Part A — Signatures & Architecture

### A1. `ContextBudgetService` class signature

```typescript
// packages/core/src/modules/context-budget/context-budget.service.ts

import { Injectable, Logger } from '@nestjs/common';
import { EventBusService } from '../events/event-bus.service.js';
import { EVENT_CHANNELS } from '../events/event-channels.js';
import { ProjectRegistryService } from '../project-registry/project-registry.service.js';
import type { ReadableSpan } from '@opentelemetry/sdk-trace-base';
import type { RunningTotal, ContextBudgetThresholds } from './context-budget.types.js';
import {
  ATTR_GEN_AI_INPUT_TOKENS,
  ATTR_PROJECT_ID,
  ATTR_SESSION_KEY,
  DEFAULT_THRESHOLDS,
} from './context-budget.constants.js';

@Injectable()
export class ContextBudgetService {
  private readonly logger = new Logger(ContextBudgetService.name);

  /** Per-session accumulator (A2). */
  private readonly totals = new Map<string, RunningTotal>();

  constructor(
    private readonly eventBus: EventBusService,
    private readonly projectRegistry: ProjectRegistryService,
  ) {}

  /**
   * Ingest a single ended span. Called by ContextBudgetSpanProcessor.onEnd.
   *
   * - Pure synchronous: reads span.attributes, mutates this.totals, emits events.
   * - I-1 safe: NO LLM calls. Reads only attributes Claude Code already populated.
   * - Resilient: missing attribute → no-op (no throw, no event).
   * - Idempotent emission: nearLimitFired and forceHandoffFired flags ensure one
   *   event per session per threshold (charter F4 graceful end semantics).
   */
  ingestSpan(span: ReadableSpan): void;

  /** Test/admin helper: clear state for a session (e.g., on session.ended). */
  resetSession(sessionKey: string): void;

  /** Test helper: snapshot of current totals (returns a copy, not a live ref). */
  snapshot(sessionKey: string): RunningTotal | undefined;

  // ── private ──
  private resolveThresholds(projectId: string | undefined): ContextBudgetThresholds;
  private extractInputTokens(span: ReadableSpan): number | undefined;
  private extractSessionKey(span: ReadableSpan): string | undefined;
  private extractProjectId(span: ReadableSpan): string | undefined;
}
```

**Lifecycle hooks**: `ContextBudgetService` does NOT implement `OnModuleInit` / `OnModuleDestroy`. It is a stateless-on-construction DI singleton. The state (`totals` Map) lives for the daemon's process lifetime — we do not persist it (Karpathy P2: simplicity; if the daemon restarts, in-flight session tokens are reset, which is correct behaviour because session restart implies a fresh CC subprocess anyway).

**Lifecycle ownership of the SpanProcessor** lives on `TracingModule` (see A7) — not on `ContextBudgetService` — because the processor is a tracing-pipeline citizen and must be registered/torn down with the tracer provider.

### A2. State shape — `RunningTotal`

```typescript
// packages/core/src/modules/context-budget/context-budget.types.ts

export interface RunningTotal {
  /** Sum of gen_ai.usage.input_tokens observed across all spans for this session. */
  inputTokens: number;
  /** Wall-clock of latest span observed for this session (for diagnostics). */
  lastSeenAt: Date;
  /** Set true the moment a near-limit event has been emitted; never reset. */
  nearLimitFired: boolean;
  /** Set true the moment a force-handoff event has been emitted; never reset. */
  forceHandoffFired: boolean;
  /** Resolved thresholds at the time of first observation (cached, not re-read per span). */
  thresholds: ContextBudgetThresholds;
  /** projectId resolved from span attributes (may be undefined if span lacked attribute). */
  projectId: string | undefined;
}

export interface ContextBudgetThresholds {
  warnAtTokens: number;        // default 200_000 (F4)
  forceHandoffAtTokens: number; // default 230_000 (F4)
}
```

**Rationale per field**:
- `nearLimitFired` / `forceHandoffFired` exist solely to make emission idempotent. Charter F4 says "graceful end" — repeated emissions would re-trigger handoff logic and loop. Once-per-session-per-threshold is the contract.
- `thresholds` is cached on first observation: a profile hot-reload mid-session must NOT shift the threshold under a session that is already approaching it. Determinism > convenience.
- `projectId` is captured from the span (not from session-key parsing) because session keys may evolve; the canonical source of project identity on a span is the `project.id` attribute (per I-15).

**Session key**: `RunningTotal` is keyed by a string `sessionKey`. Source order (first present wins):
1. Span attribute `session.key` (set by hooks-receiver on Orch-emitted spans).
2. Span attribute `claude.session_id` (set by Claude Code's native OTEL emission).
3. Fallback: `${projectId}:${trace_id}` if neither key is present.

If the span lacks ALL three (no project, no session, no traceId), the span is dropped silently — there is no session to attribute it to. (Logged at DEBUG level, never WARN, to avoid log noise from non-LLM spans.)

### A3. Span ingestion mechanism — DECISION (see `decisions/004`)

**Chosen**: **Custom `SpanProcessor`** registered against the active `BasicTracerProvider`.

**Rejected — Option 2 (Polling)**: introduces collector dependency for an in-process problem; latency unsafe near the 230K cliff.

**Rejected — Option 3 (EventBus hook)**: no per-span event channel exists today; adding one would itself be a SpanProcessor with extra serialization cost — collapses to Option 1.

`ContextBudgetSpanProcessor` signature:

```typescript
// packages/core/src/modules/context-budget/context-budget.span-processor.ts

import type {
  ReadableSpan,
  Span as SdkSpan,
  SpanProcessor,
} from '@opentelemetry/sdk-trace-base';
import type { Context } from '@opentelemetry/api';
import type { ContextBudgetService } from './context-budget.service.js';

export class ContextBudgetSpanProcessor implements SpanProcessor {
  constructor(private readonly service: ContextBudgetService) {}

  onStart(_span: SdkSpan, _parentContext: Context): void {
    // No-op. We need final attribute values, which only exist on end.
  }

  onEnd(span: ReadableSpan): void {
    // Defensive try/catch — a thrown error MUST NOT corrupt the OTLP pipeline.
    try {
      this.service.ingestSpan(span);
    } catch (err) {
      // Log via console.warn; cannot use Logger in pure SpanProcessor without DI.
      // Implementer: pass an injected Logger into the processor or accept the warn().
      // Recommended: the service catches its own errors; processor stays minimal.
    }
  }

  forceFlush(): Promise<void> {
    return Promise.resolve();
  }

  shutdown(): Promise<void> {
    return Promise.resolve();
  }
}
```

Registration (in `tracing.module.ts:onModuleInit`):

```typescript
import { trace } from '@opentelemetry/api';
import type { BasicTracerProvider } from '@opentelemetry/sdk-trace-base';
// ...
const provider = trace.getTracerProvider() as unknown as BasicTracerProvider;
// Provider may be a ProxyTracerProvider in NodeSDK — call getDelegate() if needed.
const realProvider =
  'getDelegate' in provider
    ? (provider as unknown as { getDelegate: () => BasicTracerProvider }).getDelegate()
    : provider;
realProvider.addSpanProcessor(this.contextBudgetSpanProcessor);
```

Implementer note: NodeSDK wraps the provider in a `ProxyTracerProvider`. The runtime `getDelegate()` access is a known OTEL escape hatch. If the cast becomes problematic, switch to passing the SpanProcessor into bootstrap via a new option `BootstrapTracingOpts.extraSpanProcessors`. Note: in the cross-process case (CC subprocess emits its own spans straight to the collector), Orch's SpanProcessor only sees Orch-emitted spans. For F4 to work, Orch must observe the token deltas. Two options:

- **(7a)** Hooks-receiver, on receipt of every PostToolUse / Stop / SessionEnd hook from CC, opens a short Orch span and copies `gen_ai.usage.input_tokens` from the hook payload onto the span as an attribute. **Implementer Task 3.2 chooses 7a** — produce a tiny Orch span per relevant hook event whose attributes mirror the hook payload's token fields. The hooks-receiver already exists; this is a single attribute-copy in the existing hook handler. Confirm with the hooks-receiver maintainer / module before changing it. If the hook payload schema does not currently surface `gen_ai.usage.input_tokens`, fall back to opening the span via `TracingService.withSpan` inside the hook handler with explicit `setAttribute('gen_ai.usage.input_tokens', value)` from the payload.

### A8. I-1 guardrail statement

## Risks

1. **NodeSDK provider opacity.** The `NodeSDK` from `@opentelemetry/sdk-node` does not expose its internal `BasicTracerProvider` directly. The implementer must use `trace.getTracerProvider()` + `getDelegate()` or extend `BootstrapTracingOpts` with `extraSpanProcessors`. Decision-rationale documented in `decisions/004`. If the OTEL API surface in our installed version differs, fall back to bootstrap-time injection.

2. **Hook-payload-to-span attribute bridge (A7 sub-decision 7a).** Implementer must verify `gen_ai.usage.input_tokens` is actually populated on the spans the SpanProcessor sees. If hooks-receiver is the only Orch-emitted span site and it doesn't currently set token attributes, this task includes a SMALL hooks-receiver edit to set those attributes from the hook payload. If the hook payload itself lacks them, escalate to phase-3 master-planner — F4 fundamentally requires the data plane to surface tokens.

3. **Threshold cache vs hot-reload.** A profile hot-reload mid-session does NOT update an already-active session's thresholds (cached on first observation). This is intentional (determinism) but counter-intuitive — document it in service JSDoc and a session log.

4. **Critical-event policy for `session.context_near_limit`.** Currently NOT in `CRITICAL_SSE_TYPES`. If product feedback in Phase 3 says "the warning was dropped during a burst," promote it. Do not promote in 3.2 without evidence (P2: simplicity).

5. **Cross-session token accounting confusion.** When CC sessions hand off (Task 3.5+), the new session is a NEW `claude.session_id`. RunningTotals are per-session, so the new session correctly starts at 0. Confirm with one explicit test once Task 3.5 lands (out of scope here, but flag in handoff).

6. **Spawned-mode rationalisation note.** This plan was produced in `ORCH_SPAWNED=true` mode. No interactive clarifications were used. The most charter-consistent decomposition was chosen at every fork (SpanProcessor over polling, hyphen-case EventBus + underscore-case SSE matching existing conventions, cached thresholds for determinism).
