## Goal (verifiable outcome)

A `SchedulerModule` that, on daemon boot, registers a `node-cron` job for every
`(projectId, cronName, cronExpression)` triple declared under each project
profile's new `cron:` map. On each tick, the matching job calls
`QueueService.enqueue()` with a deterministic dedup key
(`cron:<projectId>:<cronName>:<isoMinuteBucket>`) so re-firing within the same
minute is a no-op. Bad cron expressions are rejected at profile-load time by
the zod schema; if any slip past, the service logs + emits
`scheduler.cronInvalid` and skips. Restart semantics are deliberately simple:
schedules are recomputed from current profiles; **no missed-tick replay**
(P2 — simplicity wins; the operator can re-drop a plan file if a tick was
missed during downtime).

No LLM calls (I-1). No project-specific names (I-2). All input zod-validated
(I-10). Every state change emits a log + an OTEL span event (I-11).

## A.2 SchedulerService class signature

**File**: `packages/core/src/modules/scheduler/scheduler.service.ts` (NEW)

```ts
@Injectable()
export class SchedulerService implements OnModuleInit, OnModuleDestroy {
  private readonly logger = new Logger(SchedulerService.name);
  /** projectId → cronName → ScheduledTask handle. */
  private readonly jobs = new Map<string, Map<string, ScheduledTask>>();
  /** Unsubscribe handles for project.* events. */
  private readonly unsubs: Array<() => void> = [];

  constructor(
    private readonly registry: ProjectRegistryService,
    private readonly queue: QueueService,
    private readonly eventBus: EventBusService,
    private readonly tracing: TracingService,
  ) {}

  async onModuleInit(): Promise<void> { /* register all current projects + subscribe */ }
  async onModuleDestroy(): Promise<void> { /* stop+remove every ScheduledTask, unsubscribe */ }

  /** Public for test. Returns count of registered jobs across all projects. */
  jobCount(): number;
  /** Public for test. Returns immutable snapshot for assertion. */
  listJobs(): ReadonlyArray<{ projectId: string; cronName: string; expression: string }>;
}
```

**Decision points resolved**:
1. **Global service, not per-project**: matches `QueueService` and `ProjectRegistryService` shape; charter F8 (one daemon → N projects); avoids dynamic NestJS module per project. Picked **global**.
2. **`node-cron` (not `cron`)**: phase plan §3.7 names it; widely used; built-in `validate()`; no decision-doc override needed.
3. **Hot-reload**: subscribe to `project.registered` / `project.updated` / `project.removed` and re-register jobs for that project only. Charter N6 (72h stable) is satisfied — full daemon restart is NOT required for profile changes since `ProjectRegistryService` already broadcasts these events. Cost is small (rebuild a Map slot).
4. **Tick-handler error handling**: enqueue failure → log + span error attribute, do NOT retry inside scheduler (`QueueService` owns retry semantics via attempts/quarantine — Karpathy P2). The dedup key prevents duplicate enqueue if the next minute fires before the failure is observed.

## A.3 profile.yaml schema extension

**File**: `packages/core/src/domain/profile.ts` (MODIFY — additive only)

Add a new optional field to `ProfileSchema`:

```ts
/**
 * Cron-driven plan enqueue map (Task 3.7).
 *
 * Keys are unique cron names within the project (URL-safe). Values are
 * five-field cron expressions (node-cron format: `m h dom mon dow`).
 * The cron NAME is also the plan filename stem: cron name `daily-signals`
 * enqueues the plan at `{rootPath}/session-plans/pending/daily-signals.md`.
 *
 * I-2: keys are operator-defined. No project-specific defaults.
 * I-10: malformed expressions are rejected at parse-time via refine().
 *
 * Example:
 *   cron:
 *     daily-signals: "0 9 * * *"
 *     hourly-watch:  "0 * * * *"
 */
cron: z
  .record(
    z.string().regex(/^[a-z0-9][a-z0-9-]*$/, 'cron name must be lowercase URL-safe'),
    z.string().min(1).refine((expr) => cronExpr.validate(expr), {
      message: 'invalid cron expression (expected 5 fields: m h dom mon dow)',
    }),
  )
  .default({}),
```

**Where the validator comes from**: import `validate` from `node-cron` at top of `profile.ts` as `import { validate as cronValidate } from 'node-cron';` — the validator is pure (no scheduling side effect). This keeps the zod refine deterministic and offline-safe (I-13).

**Type impact**: `Profile.cron: Record<string, string>` is automatically inferred — no manual TS edits.

## A.4 Cron expression validation strategy

Use `node-cron`'s built-in `validate(expression: string): boolean` from the zod
`refine()`. Reasoning:
- `node-cron` is the runtime — single source of truth for "would this schedule".
- Avoids re-parsing in two places; if `node-cron` accepts, the runtime won't throw.
- A second-line defense lives in SchedulerService: when registering a job, wrap
  `cron.schedule()` in try/catch; on throw, emit `scheduler.cronInvalid` and
  skip (the schema should catch this, but defense-in-depth is cheap).

`scheduler.cronInvalid` is the runtime's escape hatch; the schema's
`safeParse` failure path is the load-time gate (already wired through
`ProjectRegistryService.readAndParseFile()` → `project.invalid` event).

## A.5 Tick handler — cron name → plan path → enqueue shape

```ts
private async onTick(projectId: string, cronName: string, expression: string): Promise<void> {
  const project = await this.registry.getProject(projectId);
  if (project === undefined) return; // raced with project.removed

  const planPath = path.join(
    project.rootPath,
    'session-plans',
    'pending',
    `${cronName}.md`,
  );
  // Minute-bucket dedup key: same cron firing twice in the same wall minute
  // is collapsed by QueueService's existing (projectId, dedupKey) unique constraint.
  const isoMinute = new Date().toISOString().slice(0, 16); // "YYYY-MM-DDTHH:MM"
  const dedupKey = `cron:${cronName}:${isoMinute}`;

  await this.tracing.withSpan('scheduler.tick', async (span) => {
    span.setAttribute('scheduler.projectId', projectId);
    span.setAttribute('scheduler.cronName', cronName);
    span.setAttribute('scheduler.expression', expression);
    try {
      const item = await this.queue.enqueue({
        projectId,
        planPath,
        dedupKey,
        mtime: Date.now(),
        sessionType: 'cron', // generic; not project-specific (I-2)
      });
      span.setAttribute('queue.itemId', item.id);
      this.eventBus.emit(EVENT_CHANNELS.scheduler.tickFired, {
        projectId,
        cronName,
        expression,
        firedAt: new Date().toISOString(),
        nextRunAt: this.computeNextRun(expression),
        itemId: item.id,
      });
    } catch (err) {
      span.setAttribute('error', true);
      this.logger.error({ msg: 'scheduler.tick:enqueue-failed', projectId, cronName, error: String(err) });
      // Do NOT retry — QueueService owns retry. Do NOT throw — node-cron would log+swallow anyway.
    }
  });
}
```

**`computeNextRun`** is a small helper. `node-cron@4.x` does not expose a public next-run API; use a tiny fallback: parse the expression with `cron-parser` ONLY IF it's already a transitive dep — otherwise omit `nextRunAt` from the event payload (mark as optional in the schema). **Decision: keep `nextRunAt` optional** to avoid pulling a second cron lib (P2). If the brief reviewer wants it mandatory, add `cron-parser` as a separate decision doc.

## A.7 Restart semantics — no replay

On `onModuleInit`:
1. `await this.registry.listProjects()` and call `registerProject(profile)` for
   each.
2. Subscribe to `project.registered`, `project.updated`, `project.removed`
   via `eventBus.on(...)`. Store the unsub fns in `this.unsubs`.
3. Log a single summary line: `scheduler:boot { totalProjects, totalJobs, skippedInvalid }`.

`registerProject(profile)` flow:
- If a slot for `profile.projectId` already exists in `this.jobs`, call
  `unregisterProject(profile.projectId)` first (covers the `updated` case).
- For each `(cronName, expression)` in `profile.cron`:
  - Call `cron.schedule(expression, () => void this.onTick(...))`.
  - On thrown exception: emit `scheduler.cron-invalid`, log warn, skip entry.
  - On success: store handle, increment counter.

`unregisterProject(projectId)`:
- For each handle in the project's slot, call `task.stop()` (node-cron API).
- Delete the slot from `this.jobs`.

`onModuleDestroy`:
- Iterate every slot, call `task.stop()` on every handle.
- Call every fn in `this.unsubs`.
- Log: `scheduler:shutdown { stoppedJobs }`.

**Replay**: deliberately not implemented. If the daemon was down at 09:00 when
`daily-signals` should have fired, the next fire is the *next* 09:00. The
operator can manually drop the plan file to recover. This is documented in the
service docstring and traced to Karpathy P2.

## Risks

- **R-1 (architect-side)** — `node-cron` v4 API drift. The brief assumes
  `cron.schedule(expr, fn) → ScheduledTask` with `.stop()`. If v4 changed this
  (e.g., a `Task` class with `.destroy()`), sandwich-dev should adapt and note
  the diff in the session log. No decision doc needed unless the API requires
  a shape change to A.5/A.7.
- **R-2** — `nextRunAt` in `scheduler.tick-fired` payload is optional because
  computing it cheaply requires either `node-cron` exposing `nextRun()` (v4
  may; older versions don't) or pulling `cron-parser`. Picked optional to
  preserve P2 simplicity. If a downstream consumer requires it, promote in a
  follow-up.
- **R-3** — Minute-bucket dedup key has a 1-minute granularity. If an operator
  configures two different cron expressions that both fire at the same wall
  minute and both map to the same plan filename (impossible because cron name
  is also the filename stem and dedup includes cron name), there is no
  collision. If the same cron fires twice in the same minute due to clock
  skew, dedup absorbs it — desirable.
- **R-4** — Profile hot-reload has a small race: a tick handler captured a
  `projectId` reference that is removed before `onTick` resolves the registry
  lookup. Handled: A.5 returns early if `getProject` returns undefined.
- **R-5** — MAJ-B is intentionally not addressed. If sandwich-dev encounters
  an unexpected dependency on the duplicated `IAGENT_RUNTIME` provider while
  wiring SchedulerModule, STOP — escalate, do NOT touch handoff/sessions
  files.
