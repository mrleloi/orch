## Methodology limitation acknowledgment

The session-log mtime proxy measures the orchestrator serial log-write batches, NOT actual subagent parallel-execution overlap. Even though substages 6.1/6.2/6.3 ran tasks in parallel (verified by Phase 5 wallclock data + master plan sec4 estimates of 30-50% improvement + 6.3 dispatch graph showing 5 turns vs 8 forced-serial = ~37.5%), this proxy cannot resolve the parallelism - log files are written serially as the orchestrator processes subagent returns, so wallclock_actual is approximately wallclock_serial_baseline, yielding improvement ratios near 0 (8.0% / 0.9% / 0.4% observed).

Two future-improvement proxies for v2.2 / 6.5:
(a) Record actual subagent dispatch + completion timestamps in budget-tracker.md or a dedicated dispatch.jsonl.
(b) Extract per-task wallclock from the implementer task-notification trace (which has dispatch + completion times via the orchestrator transcript).
(c) OTEL span-based timing.

The implementation is honest - the script correctly computes what its data source can measure. The defect is in the proxy methodology, not the code.
