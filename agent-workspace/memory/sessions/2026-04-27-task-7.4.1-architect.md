### Why hook names are not scripts

The Phase 6 rollup component_type `hook` with names like `Bash`, `Read`, `Edit` etc. are Claude Code built-in tool types. The telemetry hook `scripts/hooks/component-telemetry.sh` fires on PreToolUse/PostToolUse for ALL tool calls — including built-in Bash executions, file reads, etc. These get recorded as `component_type: "hook", component_name: "Bash"` (or whatever the Claude Code tool name is).

The Decision 024 map `hook::<name>` → `scripts/hooks/<name>.sh` was designed for custom hook script registrations (like `hook::component-telemetry` resolving to `scripts/hooks/component-telemetry.sh`). The built-in tool event types were not contemplated in that map.

The two-tier exemption in the spec §4 and §13 correctly handles this: PASS check happens first (step 3), then EXEMPT for known builtins (step 4). Custom hook scripts that DO have a matching .sh file resolve via PASS before reaching the EXEMPT check.

## Inline function analysis (lines 98-109 of feedback-loop.spec.ts)

The inline function has exactly this shape:

```typescript
function lintRecommendationsCitations(recsMd: string): { violations: string[] } {
  const violations: string[] = [];
  const lines = recsMd.split('\n');
  let currentSection = '';
  for (const line of lines) {
    if (line.match(/^## /)) currentSection = line;
    if (line.match(/^- \*\*/) && !line.includes('cites rollup row:')) {
      violations.push(`${currentSection}: ${line.slice(0, 80)}`);
    }
  }
  return { violations };
}
```

The IMPL in citation-linter.ts will export this as `lintRecommendationsCitations()` with the same signature. The return type may be enhanced to `{ violations: LintViolation[] }` where `LintViolation` includes section + line fields explicitly — this adds structure without changing the behavior. The existing feedback-loop.spec.ts Case 3 still works because it calls the inline version, not the new exported version.
