## Q1 Resolution — Stop Hook Decision JSON Shape

**Question**: `{"decision":"block","reason":"..."}` vs `{"decision":"deny","message":"..."}` vs `{"additionalContext":"..."}`?

**Decision**: Used `{"decision":"block","reason":"..."}` per:
- Source doc: `.claude/skills/claude-code-hooks/SKILL.md` — describes Stop hooks as "async-safe" but does not specify blocking JSON format directly. The doc at line 22 marks Stop hooks as `async-safe` in the sync/async column, which means Claude Code does NOT natively support blocking a Stop hook via decision JSON in the same way PreToolUse can block a tool.
- Architect doc §B signature and §E both specify `{"decision":"block","reason":"..."}`.
- INV-9 confirms: "Stop blocking is communicated via stdout JSON `{"decision":"block","reason":"..."}`, never via exit code."
- Default recommendation in Q1 (§9): `{"decision":"block","reason":"..."}` per "most recent Stop hook spec".

**Implementation choice**: Followed architect default. If Claude Code does not parse this as an actual blocking decision (given that Stop hooks are async-safe), the JSON emitted to stdout is still informative — the LLM can see it via stdout capture. The guard degrades gracefully: even if Claude Code doesn't honor the `decision:block`, the forensic alert log entry is still written. This is documented in the script header.

**Deviation from task brief**: The brief mentions "4 it-blocks" but the architect §D table has 6 test rows (3 positive + 3 negative). Implemented all 6 because the fixtures were already built for all 6 scenarios. The brief's "4" likely referred to a condensed description; the architect table is authoritative.
