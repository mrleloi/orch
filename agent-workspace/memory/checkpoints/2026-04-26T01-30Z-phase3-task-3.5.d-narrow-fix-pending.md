### BLOCKING items (must fix in narrow-fix dispatch)

1. **MAX_ITERATIONS=10 cap insufficient** (`prompt-renderer.ts:256`).
   - **Empirical evidence from reviewer**: with 100 decisions and `hardCap=800`, all 10 loop iterations exhaust into `dropped_oldest_decisions` (25% increments leave ~3 items remaining before iter cap). Loop exits without reaching Step 5 hard-truncate. Returns text=14,300 chars (17.9× the cap).
   - **Contract violation**: `result.text.length <= hardCap` MUST hold for any input.
   - **Fix recommended by reviewer**: bump MAX_ITERATIONS to 50, OR restructure the outer while-loop so each iteration progresses through ALL FIVE step categories rather than one drop-action at a time. The latter is architecturally cleaner: each iteration tries decisions → completed → diff → pickup-shorten → hard-truncate, and the loop terminates when one full pass leaves text ≤ cap. **Strong preference for restructure** — bumping MAX_ITERATIONS is a band-aid that breaks again with bigger inputs.

2. **T-CAP-3 still vacuous** (`prompt-renderer.spec.ts:196-224`).
   - Symptom of #1: passes because cap is never enforced, so the 50-pending content stays in the oversized 14,300-char output. If the cap were enforced correctly and pending alone exceeded 800 chars, hard-truncate would cut items 8-49 — and the test would correctly FAIL.
   - **Fix after #1 is corrected**: re-tune the fixture (smaller `charsPerItem` for pending, OR larger cap, OR fewer pending items) so the pending section legitimately fits and the test asserts genuine preservation. Alternative: add a separate "pathological pending overflow" test that asserts `truncated: true` + hard-truncate kind action when pending alone > cap.

3. **T-CAP-5 vacuous** (`prompt-renderer.spec.ts:264-285`).
   - Same root cause: with 20 decisions and hardCap=200, all 10 actions are `dropped_oldest_decisions`. Conditional ordering guards (`firstCompleted !== -1`, `firstDiff !== -1`, `firstPickup !== -1`) all evaluate to false. NO ordering assertion executes.
   - **Fix after #1 is corrected**: choose a fixture where each truncation step provably fires (smaller decisions/completed counts, larger pickup, modest cap). Assert the action sequence covers all 4 step categories (decisions → completed → diff → pickup) before any hard-truncate.
