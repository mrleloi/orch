# Decision 002 — Task 1.7 uses sandwich-dev single call (not task-implementer split)

**Date**: 2026-04-24
**Context**: Phase 1 Task 1.7 (Events + Tracing modules) is MULTI_TASK_IMPL per phase-1-core.md, with 2 tightly-coupled subtasks (1.7a Events, 1.7b Tracing). The plan prescribes "task-implementer per task + spec-compliance-reviewer + code-quality-reviewer + sandwich-verifier (opus) at close" — i.e., 7 subagent dispatches total.
**Decision**: Use a single `sandwich-dev` call covering BOTH 1.7a and 1.7b in one subagent context.

## Rationale

1. **Charter P2 (Simplicity)**: 2 tightly-coupled subtasks with shared types (TRACEPARENT propagation needs both event wiring and tracing primitives) benefit from a single context. Per-task split creates an artificial seam that the sandwich-dev naturally bridges.
2. **subagent-driven-development skill trigger**: Skill says "Mandatory for MULTI_TASK_IMPL with 3+ tasks." Task 1.7 has 2 tasks — below threshold.
3. **Task 1.16 gate**: Phase 1 advances only on sandwich-verifier (opus) adversarial review at Task 1.16. That gate catches any quality gap from skipping the per-task 2-stage review here.
4. **Budget discipline**: Per-task flow would spend ~50-100K in completion notifications on orchestration alone; single sandwich-dev keeps main session lean enough to reach Task 1.9 before reboot.
5. **Precedent**: Tasks 1.3 (state machine, 80K, complex), 1.4 (Prisma, 60K), 1.6 (registry, 80K) all executed via single sandwich-dev with all gates passing.

## Risks accepted

- No per-task spec-compliance snapshot — mitigated by explicit gate list in the brief + Task 1.16 adversarial close.
- If 1.7a and 1.7b have independent failure modes, a single subagent might partial-succeed. Mitigation: brief instructs BLOCKED status with specifics; orchestrator can retry 1.7b separately if needed.

## Reversibility

If 1.7 returns DONE_WITH_CONCERNS or BLOCKED, switch to task-implementer + two-stage review for the remaining subtask. Low cost to switch.

## Applies to future tasks

- Task 1.8 (Queue module, MULTI_TASK_IMPL, 180K) — evaluate at dispatch time; likely sandwich-dev given precedent.
- Task 1.9 (Sessions split into 4, 230K) — MORE subtasks, budget near cap. Reconsider: task-implementer per subtask may be justified there because of the 4-way split and adapter complexity (I-3 grep critical). Decide at dispatch.
