# Decision 013 — 5.3.8 Scope Adjustment

## Problem

Phase 5 master plan §3 row 5.3.8 reads:

> `max_concurrent_sessions` profile field + dispatcher loop

implying the field is to be ADDED. The 5.3.1 architect, reading the actual
profile schema, found that `maxConcurrentSessions` already exists at
`packages/profile/src/profile.schema.ts:185` (per-project, default 1, NO
upper bound).

Therefore the original task scope ("add the field") is partially obsolete.

## Decision

**5.3.8 scope is REDUCED to three deliverables**:

1. **Add `.max(8)` to the existing zod schema** (1-line change at
   profile.schema.ts:185). The hard cap of 8 is the sanity rail per
   master plan SC-8 + claude-code-learn §SQLite-Concurrency observation
   (subscription rate-limits dominate beyond ~6 concurrent sessions).
2. **Wire `dispatcher.service.ts` to respect the per-project cap** by
   counting `claimedBy IS NOT NULL AND claim_expires_at > NOW()` rows for
   that project before claiming the next item.
3. **Integration test**: profile with `maxConcurrentSessions: 2`, queue 4
   items across 2 projects, instrument active-count snapshots every 50ms
   over 3s, assert `max(snapshots) ≤ 2` per project.

Field schema:
```typescript
maxConcurrentSessions: z.number().int().min(1).max(8).default(1),
```

## Rationale

1. **Karpathy P3 (Surgical Changes).** The field already exists; re-adding
   it would shadow user values and require migration.
2. **Karpathy P2 (Simplicity First).** No new field, just one constraint
   tightening (`.max(8)`) + dispatcher wiring + test.
3. **Hard cap of 8 is empirically grounded.** claude-code-learn research
   notes ~6 concurrent CLI sessions saturate Anthropic subscription limits
   for typical Pro tier; cap of 8 leaves headroom for occasional bursts
   without inviting runaway concurrency.
4. **Per-project cap, not global.** Different projects may have different
   intensities; global cap can be added in v2.1 if telemetry shows cross-
   project contention.

## Affected files
