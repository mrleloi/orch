# Decision 022 — INV-10 Reporter Approach: Informational Reporter

## Context

Carryforward #11a (`tests/hooks/mode-c-guard.spec.ts:152`) and #11b (`tests/hooks/api-truncation.spec.ts:{118,153}` + `tests/hooks/narration-grep-refinement.spec.ts:{105-106}`) all share one symptom: a `expect(result.durationMs).toBeLessThan(N)` assertion against the wallclock-elapsed time of a real `spawnSync` subprocess call. On Windows Git Bash, `bash` startup overhead is non-deterministic — observed 200-450ms baseline plus intermittent 4500ms spikes — making the threshold flake at 100% rate (mode-c-guard 540-580ms vs 500ms = always fails) or load-dependently (1000ms threshold for api-truncation + narration-grep, fires under contention).

Phase 6 §F retrospective recommended a fix and labelled it "INV-10 reporter pattern". The retrospective's textual description named `vi.useFakeTimers()` + `vi.advanceTimersByTime()` — but that label is **wrong** when checked against the actual landed code in `tests/hooks/tool-call-first.spec.ts` (the 6.1.3 fix). 7.0.1 research-scanner caught this discrepancy with live grep:

```
CMD: grep -n "useFakeTimers|advanceTimers|fakeTimers|FakeTimers" tests/hooks/tool-call-first.spec.ts
RESULT: (no output — 0 matches)

CMD: grep -nE "useFakeTimers|advanceTimers|fakeTimers|FakeTimers" tests/hooks/
RESULT: (no output — 0 matches across the entire hooks suite)
```

Zero `useFakeTimers` in the entire `tests/hooks/` tree. The 6.1.3 fix is something else.

## What the actual INV-10 reporter pattern IS (verbatim, lines 16-21 + 77-92 of `tests/hooks/tool-call-first.spec.ts`)

```typescript
// INV-10: durations reported informationally; cross-platform timing flake
// (Windows Git Bash subprocess overhead spikes to ~4500ms intermittently)
// makes a hard threshold non-deterministic. Reporter pattern matches
// component-telemetry.spec.ts:35 + afterAll convention. Phase 6.1.3.
// Rationale: phase-6-v2.1-absorption.md SC-20.
const lintDurations: number[] = [];

// ... (lines 38-53: each runLint() pushes Date.now() delta into lintDurations) ...

afterAll(() => {
  // INV-10 informational reporter (replaces the per-call wallclock assertion
  // that was flake-prone on Windows Git Bash; Phase 6.1.3 fix).
  // Rationale: phase-6-v2.1-absorption.md SC-20.
  if (lintDurations.length > 0) {
    const sorted = [...lintDurations].sort((a, b) => a - b);
    const median = sorted[Math.floor(sorted.length / 2)] ?? 0;
    const p99 = sorted[Math.floor(sorted.length * 0.99)] ?? sorted[sorted.length - 1] ?? 0;
    console.log(
      `\n[INV-10 reporter] tool-call-first-lint.sh latency — n=${lintDurations.length} median=${median}ms p99=${p99}ms`
    );
  }
  // ... (cleanup) ...
});
```

Three load-bearing properties:

1. **Module-scope accumulator** (`const lintDurations: number[] = []` at line 21) — collects every per-call duration.
2. **Per-call push** (line 53 `lintDurations.push(durationMs)`) — but ZERO `expect(...)` assertion against duration in any `it()` block.
3. **`afterAll` reporter** (lines 77-92) — sorts, computes median + p99, `console.log` only. Vitest captures stdout; the line appears in the test report as informational diagnostic. Test count is unaffected.

## Decision

Adopt the **informational reporter** pattern for #11a and #11b. Specifically:

- **REMOVE** `expect(result.durationMs).toBeLessThan(N)` from all 4 sites:
  - `tests/hooks/mode-c-guard.spec.ts:152` (was `< 500`)
  - `tests/hooks/api-truncation.spec.ts:118` (was `< 1000`)
  - `tests/hooks/api-truncation.spec.ts:153` (was `< 1000`)
  - `tests/hooks/narration-grep-refinement.spec.ts:106` (was `< 1000`)
- **ADD** module-scope `const <slug>Durations: number[] = []` accumulator at top of each affected spec file.
- **ADD** `<slug>Durations.push(result.durationMs)` (or equivalent — the runners already record `durationMs`) at each call site.
- **ADD** `afterAll()` reporter at the end of each spec file that mirrors lines 78-87 of `tool-call-first.spec.ts` verbatim (rename `lintDurations` to per-spec slug; rename console.log label to identify the script under test).

## Alternatives Considered

### Alternative (i) — `vi.useFakeTimers()` + `vi.advanceTimersByTime()` (the phase-6-complete.md §F label)

**REJECTED. Architecturally wrong for this shape.**

`vi.useFakeTimers()` replaces JavaScript's `setTimeout`/`setInterval`/`Date` inside the **vitest worker process**. It does NOT control the wallclock observed across `spawnSync('bash', [SCRIPT_PATH], …)`. The subprocess runs in a **separate OS process** with its own real-time clock; the `durationMs = Date.now() - start` measurement straddles the spawnSync boundary, where `Date.now()` is the OS-level system clock. Even if `vi.useFakeTimers()` is active in the test process, the `Date.now()` calls before/after `spawnSync` would either still report real wallclock (if `Date` is one of the unmocked APIs in the active config), or — if mocked — would freeze at the fake timestamp on both sides, returning `0ms` regardless of subprocess actual wall time. Either outcome breaks the assertion.

Fake timers are correct for testing in-process timer logic (e.g., `setTimeout(fn, 5000)` resolves after `vi.advanceTimersByTime(5000)`). They are wrong for testing real-subprocess wallclock latency.

### Alternative (ii) — `process.platform === 'win32'` skip/threshold gate

**REJECTED. Hides the signal on the most common dev workstation.**

CLAUDE.md explicitly establishes Windows / Git Bash as the primary dev environment for this project. `it.skipIf(process.platform === 'win32')` would silently disable the assertion on the workstation where the test gets the most exercise, leaving it active only on hypothetical Linux/macOS CI (which this repo does not currently run). A regression introduced on Windows would land green; a regression introduced on Linux would surface, but that's not where most code is written.

Live grep `grep -nE "process\.platform" tests/hooks/` shows 2 existing references (`session-self-reboot-parse.spec.ts:31` and `component-telemetry.spec.ts:373`) — both for legitimate platform-dispatch reasons (path-separator handling, signal-name differences). Adding 4 more for timing-gate purposes would increase the platform-shim surface for the wrong reason and erode the test suite's cross-platform claim.

### Alternative (iii) — Threshold raise (e.g., 500 → 1500ms)

**REJECTED. Insufficient.** Three of the four flake sites already use `< 1000ms` and still flake under load. The flake is load-dependent, not threshold-dependent. Doubling the threshold to 2000ms might reduce flake rate to ~5% but does not eliminate it; informational reporter eliminates it 100%.

## Trade-offs

| Property | Hard assertion (status quo, flaky) | Informational reporter (Decision 022) |
|---|---|---|
| Determinism on Windows | 0% (or 95% under load) | 100% |
| Regression detection | YES — fails build if subprocess gets 2× slower | NO — must read stdout |
| Diagnostic visibility | Only on FAIL | EVERY run (median + p99 in test output) |
| LOC delta | 0 | +6-8 lines per spec file |
| Cross-platform | Inconsistent (passes Linux, flakes Windows) | Uniform |

The trade-off is **regression detection vs determinism**. We choose determinism because:
- The current "regression detection" is broken (false positives drown signal).
- The reporter prints stats every run; a human or future automation can monitor the median trend (e.g., grep `median=` from CI logs).
- A future SC-X can re-introduce a bounded assertion against the *median* once enough data establishes a stable baseline (P99 still informational).
