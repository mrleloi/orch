# Decision 025 — SC-39 Defer to v2.3

## Context

SC-39 is the optional Phase 7 success criterion: produce ≥1 actionable proposal from the self-evolution loop's first real run against accumulated telemetry. The Phase 7 master plan §2 marks SC-39 as **deferrable** if signal is thin. 7.0.2 must lock the go/no-go before 7.7 dispatches anything.

7.0.1 research-scanner gathered live evidence:

### Live Phase 6 telemetry rollup (from `component-rollup-phase-6.md` — 14 components, 2590 events)

| Type | Name | Count | Success Rate | p99 Dur (ms) |
|---|---|---|---|---|
| hook | Bash | 1072 | 1.000 | 117915 |
| hook | Write | 135 | 1.000 | 431195 |
| agent | unknown-agent | 75 | 1.000 | 190702 |
| ... (11 more rows, all `success_rate == 1.000`) | | | | |

### RULE evaluation against this data (live result, per 6.2.7 P1 verifier)

| Rule | Condition | Fires? | What it would propose |
|---|---|---|---|
| RULE-1 | `p99_duration_ms > 60000 AND model == sonnet` | YES — `agent::unknown-agent` (p99=190702ms) | "Tier-down unknown-agent" |
| RULE-2 | `count >= 5 AND success_rate < 0.6` | NO — every component has 1.000 success | (no proposal) |
| RULE-3 | `count >= 3 AND top_failure_mode == "C"` | NO — zero Mode-C events captured | (no proposal) |
| RULE-4 | `component_type == "agent" AND p99_tokens_real > 100000` | NO — telemetry doesn't capture per-agent tokens this way | (no proposal) |

Only RULE-1 fires. And it fires on `unknown-agent` — which 6.2.7 P1 documented as **a data-capture artifact**, not a real agent type. The SubagentStop hook does not currently capture the agent identifier reliably; events from un-identified agents land in the `unknown-agent` bucket. A proposal to "tier-down unknown-agent" is architecturally meaningless: there is no such agent to tier-down.

## Decision

**DEFER SC-39 to v2.3.** Substage 7.7's deliverable is a **2-page rationale document** (`agent-workspace/memory/phase-7-routing-recommendations.md`), NOT a loop execution.

The rationale document must contain:
1. The RULE evaluation table above (re-run live against Phase 6 + Phase 7 telemetry combined at 7.7 time).
2. Citation of 6.2.7 P1 verifier finding that `unknown-agent` is a data-capture defect.
3. v2.3 prerequisites for re-evaluating SC-39:
   - Fix the SubagentStop hook to capture agent identifiers reliably (Phase 8 candidate item).
   - Accumulate ≥5× current event volume (target: ~12-15K events post-Phase 7).
   - Verify ≥2 RULES fire on real components (not data-capture artifacts).

If at 7.7 dispatch time, telemetry analysis shows ≥2 of RULE-2/3/4 firing on real (non-`unknown-agent`) components, the master plan permits switching from DEFER to EXECUTE — but the architect for 7.7 MUST write a supplementary decision file documenting the signal change before dispatching IMPL.

## Why DEFER is correct

### Performative vs actionable

A loop run today produces a proposal about a hook-instrumentation defect, not a routing improvement. The whole point of the self-evolution loop is to convert telemetry into actionable architectural change. Running it on signal-thin data produces:

- A proposal that "tier-down unknown-agent" — vacuous, since no such agent exists in the agent registry.
- Optional human-review checkpoint that would correctly REJECT the proposal as malformed.
- A loop closure that demonstrates the loop CAN run end-to-end — a demonstration already covered by 6.2.7 P1's adversarial dry-run.

Executing the loop now is **performative theater**: ticking the SC-39 box without delivering the value SC-39 represents.

### Charter alignment

Phase 7's theme is **HARDENING**. The master plan §1 explicitly: "harden v2.1, do not extend feature surface". Producing a self-evolution upgrade that adds a real proposal-application path WOULD extend feature surface, even if the proposal itself is rejected. DEFER preserves the hardening charter.

### Cost saved

Master plan §3 budgets 7.7 at 0-220K depending on this decision:
- DEFER: ~30K (just the rationale doc)
- EXECUTE: ~200K (architect + 1-2 IMPL + verifier)

DEFER saves ~170K of opus/sonnet budget that can be redirected to v2.3 entry, where the upgrade will land on real signal.

## Reversibility

HIGH. Loop infrastructure (rollup-telemetry.ts, telemetry-analyst subagent, citation-linter) all landed in 6.2 + 7.4. v2.3 needs only an architect+IMPL pair to land the first concrete upgrade. No code is removed by deferring.

## Alternatives Considered

### Option (b) — EXECUTE 7.7 with documented caveats

REJECTED. Produces performative output. Even with caveats, the artifact is a record of "loop ran and proposed a vacuous thing", which:
- Adds noise to the recommendations corpus that future runs will have to sift past.
- Risks future operators treating the historical proposal as precedent.
- Burns 200K of budget for no actionable signal.

### Option (c) — Partial-execute with rule-set narrowing (e.g., only run RULE-2/3/4)

REJECTED. Filtering RULES to exclude RULE-1 is itself a non-trivial design decision that should not be made implicitly. If RULE-1's fire is meaningless on `unknown-agent`, the right fix is to gate RULE-1 to exclude `unknown-agent` agents — but that's a Phase 8 telemetry-analyst skill amendment, not a v2.2 loop run.
