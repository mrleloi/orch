# Decision 019 — Real-World SC-18 Verification Method

## Problem

Phase 5 SC-18 proved 75% wallclock improvement on a 200ms-per-task synthetic
fixture. Phase 6.4 must produce the same proof on production load. Options
range from "replay telemetry from a real Phase 6 substage run" to "stand up
a long-lived StockForge session and observe across N days".

## Decision

**Production-telemetry replay** — measure SC-18 from Phase 6.1+6.2+6.3's own
substage executions.

Mechanism:
1. `scripts/benchmarks/sc18-realworld.ts` reads `component-telemetry.jsonl`
   for substages 6.1/6.2/6.3 + their per-task session logs.
2. For each substage, computes:
   - actual_wallclock = max(task end_ts) - min(task start_ts) across substage
   - serial_baseline = sum(task duration_ms) (forced-serial reconstruction)
   - improvement = 1 - (actual/serial)
3. Asserts ≥35% improvement (Phase 5 retrospective §3.5 empirical band) on
   ≥2 of the 3 substages.
4. Emits `agent-workspace/memory/sc18-realworld-result.md` for SC-19 evidence.

Why not live-run: a 72h+ wallclock soak adds calendar days with no new
information; the telemetry IS the production load (subagent dispatches are
real LLM calls with real I/O). Synthetic 75% number was an upper bound;
real-world band 35-50% is the actual claim per retrospective §3.5.

## Charter Reference

- §3 time as first-class metric.
- Karpathy P2 simplicity (replay deterministic; live-run adds wallclock without
  evidentiary value).
- I-6 — replay produces only one new file; no commit pressure.

## Consequences

- Enables: empirical real-world SC-18 number as v2.1 release evidence.
- Requires: 6.1/6.2/6.3 substages must execute with telemetry hook active
  (already true post-INV-S9 fix).

## Reversibility

Trivial. The replay script is one TS file producing one MD file; remove
both to revert.
