# Decision 016 — OTLP Env-Var Propagation Strategy

## Problem

Phase 5.3.6 audits and fixes adapter env-var propagation from the daemon
process to spawned `claude` subprocesses. Master plan SC-11 specifies 8
named vars to propagate, including the family `OTEL_EXPORTER_OTLP_*`.

OpenTelemetry SDK consumes a multi-member family of env vars:
- `OTEL_EXPORTER_OTLP_ENDPOINT`
- `OTEL_EXPORTER_OTLP_HEADERS`
- `OTEL_EXPORTER_OTLP_PROTOCOL`
- `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT`
- `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT`
- `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT`
- `OTEL_EXPORTER_OTLP_TIMEOUT`
- `OTEL_EXPORTER_OTLP_COMPRESSION`
- (additional members may be added by future OTel SDK versions)

Two strategies:
- **A**: Literal-list — enumerate every known OTLP var; any new var added
  to the OTel spec requires a code update.
- **B**: Prefix-glob — match any key starting with `OTEL_EXPORTER_OTLP_`.

## Decision

**B — Prefix-glob match.** The env-build helper iterates
`Object.keys(parentEnv)` and includes any key whose name starts with
`OTEL_EXPORTER_OTLP_`.

Helper signature:
```typescript
function buildPropagatedEnv(
  parentEnv: NodeJS.ProcessEnv,
  extraEnv?: Record<string, string>,
): NodeJS.ProcessEnv
```

The OTLP family is one branch of the propagation logic; the other 7 named
vars are propagated by literal name (since they are stable, single-key
contracts).

## Rationale

1. **OTel spec evolution.** OTLP is a family that grows over OTel
   releases. A literal list would silently break forward compatibility
   when a new OTLP var (e.g., `OTEL_EXPORTER_OTLP_INSECURE`) is added in
   a future SDK release — the daemon would propagate old vars but not
   the new one, and traces would break in non-obvious ways.
2. **Trivial test.** Test #5 in 5.3.1 architect §5.B.D enumerates: seed
   `process.env` with 3 OTLP vars; assert all 3 present in returned env.
3. **Bounded blast radius.** The prefix `OTEL_EXPORTER_OTLP_` is highly
   specific; the chance of a user-defined non-OTel env var with this
   prefix is negligible. If it happens, the var gets propagated to the
   subprocess — that is acceptable for v2.0 (R5 in architect §11 risk
   table).
4. **Implementation simplicity.** One `for...of` loop with one
   `startsWith()` predicate. Karpathy P2.
