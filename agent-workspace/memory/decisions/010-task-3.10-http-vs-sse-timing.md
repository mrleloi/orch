# Decision 010 — Task 3.10 HTTP-as-Proxy vs. SSE-Listener Timing

**Date**: 2026-04-26
**Author**: sandwich-dev (Phase 3 close-out polish)
**Status**: ACTIVE

---

## Context

Task 3.10 (N5 Latency E2E Timing Harness) required asserting that queue-enqueue-to-SSE-delivery
latency is < 2000ms (charter N5). The plan specified using a Promise-based `eventBus.once()`
SSE listener to measure t0→listener-fire directly.

The Task 3.10 implementation deviated from the plan: it uses HTTP round-trip latency as a proxy
instead of a live EventBus listener. The deviation rationale in `latency.spec.ts:70-79` claimed
that "having an active EventBus listener during a Fastify HTTP request triggers an ECONNRESET"
due to `@opentelemetry/instrumentation-http` interaction with EventEmitter2.

This decision documents: (a) why the HTTP-as-proxy approach is mathematically correct,
(b) why the ECONNRESET claim is empirically questionable, and (c) the decision to keep both
variants going forward.

---

## Part A: Principled Correctness of HTTP-as-Proxy

The code path for `POST /api/v1/queue` handling is:

```
Fastify request handler
  └─ QueueController.enqueue(dto)
       └─ QueueService.enqueue(item)
            ├─ prisma.queueItem.upsert(...)   ← Transaction commits
            └─ eventBus.emit('queue.enqueued', { item })  ← synchronous
                 └─ EventEmitter2.emit(...)    ← synchronous dispatch
                      └─ all listeners fire    ← synchronous
                           └─ SseSubscription._handleEvent(...)
            return item  ← happens AFTER emit
  └─ reply.send(response)  ← HTTP response sent AFTER emit
```

Key properties:
1. **EventEmitter2 is synchronous**: `emit()` dispatches all listeners before returning.
2. **emit-inside-transaction**: `eventBus.emit` fires AFTER `prisma.upsert` commits but
   BEFORE `return item` in `QueueService.enqueue`. Therefore the entire EventBus dispatch
   completes before the HTTP response is sent.
3. **HTTP response is AFTER dispatch**: `reply.send(response)` is called after
   `QueueService.enqueue()` returns, which is after all synchronous listeners have fired.

Therefore:
```
httpLatency = (t1 - t0)
            = (time for Fastify to send the 200 response)
            ≥ (time for EventBus.emit to return)
            ≥ (time for all synchronous listeners to complete, including SseSubscription._handleEvent)
            = emitTime
```

Mathematical bound: `httpLatency >= emitTime + txCommit + auditLog >> emitTime`

Asserting `httpLatency < 2000ms` is a conservative (correct) upper bound for
`emitTime < 2000ms`. The charter N5 requirement is therefore satisfied.

---

## Part B: ECONNRESET Claim Contradicted by Empirical Evidence

The deviation rationale at `latency.spec.ts:71-79` asserts:

> "having an active EventBus listener during a Fastify HTTP request triggers an ECONNRESET"

This claim is **contradicted by `round-trip.spec.ts:294-327`**, which demonstrates that the
Promise-based EventBus listener pattern works without ECONNRESET in the same in-process test
setup:

```typescript
// round-trip.spec.ts lines 294-327 (working pattern):
const enqueuedPromise = new Promise<string>((resolve) => {
  const unsub = eventBus.on(EVENT_CHANNELS.queue.enqueued, ({ item }) => {
    unsub();
    resolve(item.id);
  });
});

const response = await supertest(app.getHttpServer())
  .post('/api/v1/queue')
  ...

const scenario1QueueItemId = await enqueuedPromise;
expect(scenario1QueueItemId).toBeTruthy();
```

This pattern (register listener BEFORE POST, await listener AFTER POST) does not produce
ECONNRESET. The `round-trip.spec.ts` tests pass consistently.

Hypothesis: The ECONNRESET in `latency.spec.ts` (if it occurred during development) may have
been caused by a different pattern — for example, registering the listener INSIDE the HTTP
response handler callback, or a race condition in how the promise was awaited concurrently
with the HTTP request.

**Conclusion**: The `latency.spec.ts:71-79` comment block was empirically incorrect as a
general claim. The correct statement is: "a specific implementation pattern caused ECONNRESET;
the `round-trip.spec.ts` pattern does not."

---

## Part C: Decision — Keep Both Variants

**Chosen: Keep both HTTP-round-trip (L1/L2) AND SSE-listener (N5) variants going forward.**

### HTTP round-trip variants (L1/L2) — keep as-is
- Serve as the **deterministic regression guard**: any latency regression in the
  enqueue-to-HTTP-response path (Prisma, EventBus dispatch, NestJS middleware) will
  show up as a timing failure.
- Mathematically correct upper bound for N5.
- Stable: no EventBus listener racing with HTTP instrumentation.

### SSE-listener variant (N5 direct) — add as close-out item #12
- Exercises the **actual SSE wire path** (`SseSubscription._handleEvent → flush → reply.raw.write`).
- Directly measures `t0 → listener-fire` rather than `t0 → HTTP-response`.
- Uses the proven-safe `round-trip.spec.ts:294-327` pattern:
  register listener BEFORE POST, await AFTER.
- Tagged as `(N5 SSE wire-path variant)` in test output.

If the SSE variant becomes flaky in CI (e.g., slow infrastructure pushes listener-fire
past 2000ms), it should be marked `.skip` with a comment referencing this decision doc,
and the HTTP variants remain the binding N5 assertion.

---

## Options Considered

### Option A: HTTP-only (current state before close-out polish)
- Pros: Stable, simple, deterministic.
- Cons: Does not directly exercise SSE wire path; verifier noted the gap.

### Option B: SSE-listener only (replace HTTP variants)
- Pros: Directly exercises the charter-specified measurement.
- Cons: Loses the deterministic regression guard for the HTTP path.

### Option C: Keep both (chosen)
- Pros: Defense in depth — HTTP guard catches latency regressions, SSE variant exercises wire path.
- Cons: +1 test; marginal CI time increase.
