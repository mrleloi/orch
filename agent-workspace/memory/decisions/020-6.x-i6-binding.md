# Decision 020 — I-6 Binding for Phase 6

## Problem

Phase 5 closed with v2.0.0 staged-but-not-committed. User redirected
to "continue development until done all" — Phase 6 builds on the staged
2.0.0 baseline. I-6 ABSOLUTE binding: zero `git commit` invocations
unless user explicitly authorizes. Question: what about the staged
v2.0.0 files? What about new v2.1 files that overlap them (e.g., a
second `package.json` version bump to 2.1.0)?

## Decision

1. **DO NOT roll back** v2.0.0 staged artifacts. They remain staged
   throughout Phase 6.
2. **DO NOT bump versions in 6.5** to 2.1.0 until the substage 6.5
   "stage v2.1" task — and even then it is staged-only, not committed.
3. **DO NOT** invoke `git commit` for ANY reason during Phase 6
   (including "small commits to checkpoint progress" — Phase 5 proved
   the project survives 28 sessions / 4 days with zero commits).
4. **Use `git add` to stage** new files as they land (consistent with
   Phase 5 5.5.4 staging discipline).
5. **Verifier gate at every substage close**: run
   `git log --oneline | wc -l` → must return `0` or
   `fatal: ... no commits yet`. Any non-zero count = STOP-3 escalation.

## Charter Reference

- I-6 ABSOLUTE: agents never commit unless user explicitly requests.
- Phase 5 retrospective §1.6 (I-6 held under sustained autonomous pressure).
- User directive 2026-04-27T~19:35Z: "no need to release now, continue
  development until done all" — explicitly NOT authorizing commits.

## Consequences

- Phase 6 ships staged v2.1 release artifacts at substage 6.5 close.
- Release commit/tag/push remains user-action (extends v2.0.0 user-action
  checklist with v2.1 entries; both can be committed in one batch when
  user authorizes).
- Verifier briefs across 6.x include explicit I-6 grep gate.

## Reversibility

N/A — this is an immutable charter binding.
