# Decision 012 — Phase 5.3 Module Paths

## Problem

Phase 5 master plan §3 (`phase-5-self-evolution.md`) and the 5.3.1 dispatch
brief specified module paths as `packages/core/src/queue/`,
`packages/core/src/sessions/`, `packages/core/src/hooks/`. The 5.3.1 architect
(reading the actual codebase) found the on-disk layout uses an additional
`modules/` segment per architecture.md §Layer 2 NestJS-module convention:

```
packages/core/src/modules/queue/
packages/core/src/modules/sessions/
packages/core/src/modules/hooks/
```

Bare `packages/core/src/{queue,sessions,hooks}/` directories DO NOT EXIST.

## Decision

**Use `packages/core/src/modules/{queue,sessions,hooks,telemetry,...}/` throughout
Phase 5.3 deliverables.** Every per-task contract in
`session-plans/pending/5.3-parallel-architect.md` cites the corrected paths.

Implementers (5.3.2 — 5.3.10) MUST match the architect doc paths verbatim. If
a contract calls a path that doesn't resolve on disk, escalate via I-2
confusion-protocol — do NOT silently relocate.

## Rationale

1. **Architecture.md §Layer 2 is canonical.** NestJS feature modules live under
   `src/modules/<feature>/`. The bare `src/` is reserved for cross-cutting
   wiring (`app.module.ts`, `main.ts`, etc.).
2. **Karpathy P3 (Surgical Changes).** Place new files where existing siblings
   live; do not introduce a new top-level layout.
3. **Drift defense.** A path mismatch between plan and reality is exactly the
   class of error that surfaces only when an implementer runs `pnpm test` and
   the import resolution fails. Fixing it once at the architect layer prevents
   N implementer-level escalations.
