# Decision 003 — Task 1.8 uses sandwich-dev (same as Tasks 1.3-1.7)

**Date**: 2026-04-24
**Context**: Phase 1 Task 1.8 (Queue module) is MULTI_TASK_IMPL at 180K budget with 4 discrete deliverable pieces (QueueRepository, QueueService, file watcher, dedup/priority). subagent-driven-development skill says "Mandatory for MULTI_TASK_IMPL with 3+ tasks."

**Decision**: Use single `sandwich-dev` call for Task 1.8. Reserve full subagent-driven-development flow (task-implementer per subtask + two-stage review per subtask + sandwich-verifier at close) for Task 1.9.

## Rationale

1. **Coupling strength**: Task 1.8's pieces are internally tightly coupled (QueueService directly uses QueueRepository; file watcher feeds QueueService; dedup/priority are properties of QueueService atomicity). Task 1.9 is explicitly split into 4 named subtasks (1.9a adapter, 1.9b request-queue, 1.9c watchdog, 1.9d manager) with distinct boundaries — THAT is where per-subtask implementation + review yields clearer robustness.
2. **Adversarial gate preserved**: Task 1.16 (`sandwich-verifier` opus, mandatory fresh context, adversarial) gates Phase 1 advancement. Any quality gap from this task appears there.
3. **Budget discipline**: Main session at ~145K; running 3-agent flow × 4 subtasks + final verifier from this session would exceed wind-down. Single sandwich-dev returns in one notification (~30K). This keeps one more hot-reboot-free task achievable.
4. **Precedent aligned**: Tasks 1.3-1.7 used single sandwich-dev; all passed gates with clean invariants.

## Scope held firm

- Task 1.9 MUST use the full subagent-driven-development flow (its 4 explicit subtasks are the canonical trigger case).
- Task 1.10 (MULTI_TASK_IMPL not explicitly listed as such in plan — it is FOCUSED_IMPL per line 283) stays sandwich-dev.
- Task 1.16 sandwich-verifier gate is non-negotiable.

## Reversibility

If 1.8 returns with DONE_WITH_CONCERNS, orchestrator retries the problematic subtask via task-implementer before moving to 1.9.
